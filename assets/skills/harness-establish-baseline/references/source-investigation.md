# 标杆来源调查与复查

## 从语义定位实现

先固定任务要比较的完整行为、实现限制和调查预算，再从 SKILL 中的公共代码仓入口选择相关来源。用户已有的参考是调查起点；同一数学行为可能使用不同 API 名称、版本后缀或融合边界，不以文件名完全一致作为找到实现的条件。

先查算子文档、导出 API 和支持列表，再沿注册/调用、host/tiling 与 kernel 核实分派。对融合实现逐项映射输入、全部输出、索引顺序、padding、容量/动态 shape、dtype 与 workspace；只有语义及允许适配已确定，才纳入构建/测试。不能把无关仓库查全作为开工门槛，也不能把明确相关的融合入口未经查看就略过。

在 BASELINE 的来源覆盖表保存仓库 URL、实际读取的 revision、检索目录/关键字/API 别名、结论和缺口。未访问、抓取失败和读不到源码只说明调查未完成，不说明不存在实现。网页读取受限时可按权限采用原仓 Git 或 raw 文件入口；仍不可访问则保留缺口，不把搜索摘要当作已读源码。

需要本地源码时，按项目管理约定放入本项目 sources 或获准 worktree，记录公共来源 URL 和实际身份；通用 skill 不依赖某个私有路径。无需为了获取代码自动安装整个框架或构建全仓，优先查所选入口的依赖与最小构建方法。

## 区分候选、包装与实现后端

每个候选需回答以下问题，详细内容可链接独立记录，不能只写一个仓库名：

| 核查项 | 保存的依据 |
| --- | --- |
| 来源与实现入口 | 公共仓库 URL、选定 revision、具体源码/API、host/tiling/kernel/测试入口；看不到的部分写 unknown |
| 后端与调用链 | 实际 AscendC/Triton/其他实现；是否调用 ACLNN、ATB、第三方 kernel 或多个阶段 |
| 语义与适配 | 原版覆盖范围、与需求的逐项差异、适配源码/开销和被排除的 case |
| 目标支持与构建 | 所需芯片/架构、SDK/依赖和配置；声明支持、编译成功和实卡通过分别记录 |
| 验证与选择 | 独立正确性证据、性能原始样本/协议或未测原因；纳入/排除理由 |

框架仓可能混有多种后端，不能将整个仓库统一称为 AscendC。多个包装调用同一底层实现时记录关系；必要时测不同公开入口，但不要当成多个独立算法证明调查充分。模板库固定具体实例、tiling 和 launch；样例必须覆盖本任务的输入/输出与比较边界才能参与性能选择。

公开源码与安装包分开标识。用安装包中的 ACLNN/ATB 计时时记录实际包、入口、加载库和版本；不能仅因名称一致就宣称执行的是最新源码。无法确认二进制与源码对应时说明分析限制；若契约要求可重建或确切源码，该缺口阻止对应验收。否则仅在允许范围内报告真实包的测量，不伪造源码对应关系。

## 有界筛选与停止

来源检索状态使用 searched / not_searched / unavailable，附范围和理由；候选资格使用 pending / eligible / excluded，正确性与性能分别使用 passed / failed / not_run / invalid / not_applicable。状态用于说明证据，不提供自动验收 gate。

- searched 无命中表示“在已查版本和范围内未发现”，不能写“AscendC 没有这个算子”。
- excluded 需要明确的语义/约束不匹配等依据；缺工具、预算不足或尚未验证保留 pending 与下一步，不写成更慢。
- 正确性失败保留反例，不进入其失败范围的常规性能评选；性能缺失也不能标成性能 failed。
- 若用户要求 AscendC，不能因暂未找到就静默改用 Triton。在约定来源范围内完成调查并说明缺口，确需放宽实现限制时引用实际用户决定。
- 停止条件来自任务预算、相关来源覆盖、剩余调查价值与具体缺口；不无限扩大到另一个算子开发项目。仅完成调查时节点可 completed，标杆仍 draft。

最终选择按测量前固定的规则执行。正确性参考与性能标杆可以不同；可用实现只有一个就报告这一事实。保留全部候选及未测范围，“最快”只能指已声明范围和可比测量，不用未知项补成排名。

## 复查与交接

首次调查在 BASELINE 记录最近来源核查、待查项与下一复查触发条件。后续 analysis 发现新 API/版本、调查遗漏、环境变化或连续无进展时，交回 establish-baseline 做相关来源的有界复查；尚无失效证据时可以继续已授权的独立分析，不为定期复查重置整条优化链。

新来源、新性能结果或用户决定形成新 BASELINE 修订，关联旧版和调查增量；旧记录保持不可变。新标杆满足全部必需条件后才发布索引，按影响决定哪些旧比较还能使用。来源有新提交本身不自动使旧测量失效；SDK/源码/协议等实际比较条件变化时才判断相应失效范围。

交给首次 analysis 的材料包含选中实现的完整调用链、实际分派及适配依据，以及尚未读到的源码范围。analysis 必须读取这些材料，不按 API 名称猜算法。长期任务的复查频率由项目约定，不写死时间间隔或强制每轮拉取远端。

## 静态审阅场景

- 普通名称检索未命中，但相关库有融合 API：继续核对语义，不提前排除 AscendC。
- 框架接口最终转调同一个 ACLNN：记录包装关系和边界，不能重复计为独立 kernel。
- 候选支持目标语义，但所需包尚未安装：pending、测试 not_run，不能排为较慢。
- 只有相同条件下已验证的实现满足契约：可发布有范围的基线，同时披露其余未测项。
- 来源出现新版本：先提案和验证，保留已冻结分母；已知条件失配的旧结果不继续当有效比较。

这些是 skill 的审阅与交接规则，不是已实现的自动源码扫描器、测量执行器或候选晋升程序。
