# 双缓冲生命周期与Cube/Fixpipe UnitFlag配对核查

## 适用症状与触发条件

- 源码有两个buffer版本，但不确定是否交替使用、是否真正重叠。
- 准备减少Cube/Fixpipe软件事件，或修改L0C数量、最终MMAD、输出顺序。
- 数据偶发错误、同步等待异常，或把“软件事件少了”直接当成性能收益。

## 核心物理机理

### 1. 双槽负责地址，依赖负责使用时机

双缓冲至少要维护两个方向的约束：

```text
写完当前数据 → 消费者才可读取该槽。
旧消费者读完 → 生产者才可覆盖该槽。
```

奇偶槽号只决定地址，不证明这两个约束成立。L1槽的消费者可能是MTE1，L0A/B槽的消费者是Cube；L1与L0的槽不是同一生命周期。

输入双槽也不表示结果有双槽。单L0C累加块必须一直保持正确部分和，并在下一个输出任务复用前保证旧结果被安全消费。

### 2. 初始化、部分和与最终交接是不同职责

跨K累加的首子步初始化结果，其余子步扩展部分和；只有最后有效K子步才能使用与最终输出匹配的交接方式。不得把流水排空循环计作额外有效K分组。

仓内 `example/gemm/example_batch_gemm.py` 当前表达：

```python
uf_partial, uf_final = 2, 3
# 普通子步使用partial，最后有效K子步使用final。
# 对应的最终acc→GM copy使用同一个final参数。
```

这是当前后端调用点的示例，不是跨平台事件号、通用开关或省略全部同步的许可。必须在项目绑定的TileLang/CANN中核对其实际参数定义与生成代码。

### 3. 硬件协议可以替代特定软件交接，但不创造输出空间

支持匹配协议的后端可能以UnitFlag表达Cube/Fixpipe交接，减少相应软件事件；输入供数、槽释放及其他消费者的依赖仍然存在。

UnitFlag不会使Fixpipe搬运零成本，也不会自动生成第二块L0C。消费者顺序或缓冲数改变时，需要重新证明旧数据不会被提前覆盖。

## 实现要点与约束

按以下顺序核查，不先手动删除事件：

1. 从输入槽、L0C与输出地址画出写者/读者及“就绪、释放”边界。
2. 在源码核对首子步清零、最后有效子步判断和最终copy；多个累加器逐个配对。
3. 在IR/CCE核对实际槽偏移、单位、清零条件、MMAD的partial/final参数与输出copy参数。
4. 明确哪些同步由编译器事件、哪些由所用硬件协议表达；没有软件FIX事件不等于没有依赖。
5. 核对实际执行覆盖、全输出正确性和流水排空，再判断目标等待是否缩短。

例如，偏移16384若以BF16元素计，对应32 KiB；如果指针类型、布局或对齐改变，同一数字不能沿用相同字节解释。

配对检查需覆盖首/末子步、槽复用和连续输出任务，而不只测试第一块结果。测试shape必须满足候选真实支持范围，不靠放宽参考或容限掩盖错误。

## 不适用边界

- 当前绑定后端没有确认相应UnitFlag语义时，不直接复制2/3参数，不按经验删除自动事件。
- 没有独立输出接收空间或释放依赖时，不能以“提前输出”或“增加stage”绕过数据竞争。
- 本卡不声称已消除任意队首阻塞；只有trace确认存在对应等待链时，才考虑 [Cube/Fixpipe队首阻塞重排卡](cube-fixpipe-hol-reordering.md)。
- 短shape的序言/排空占比与大shape不同，一次正确性通过不构成全场景协议或性能保证。

## 验证清单

- 保存实际加载源码与构建身份，并记录后端版本；公共知识卡不写死外部commit作为依赖。
- 独立参考检查完整输出，验证入口可用NaN哨兵发现漏写；不能把测试建议说成示例已经实现。
- 比较优化前后生成代码，说明软件事件变化和仍存在的槽复用依赖。
- 检查全范围最终完成、参与核覆盖及同步异常；仅局部核trace不能确认全核安全与长尾。
- 用完整kernel设备时间验收益，不累加重叠pipe跨度，不把含等待跨度视为纯服务时间。

## 证据等级与维护

现有示例支持“源码已表达配对、保留生成代码中可检查”的实现级结论；不从该事实推导某个单项实测加速比。新编译器如改变槽布局或协议，应重新验证本卡的调用方式与生成代码检查点。

此卡归类为`compiler-note`，因为参数接口、自动事件与lowering行为依赖绑定后端；若后端改变导致示例方式失效，应更新适用边界，必要时标记`superseded`，而不是继续传播旧参数。
