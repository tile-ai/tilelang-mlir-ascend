# GEMM分级分块：先算容量，再判断复用和任务局部性

## 适用症状与触发条件

- 把GM→L1的K块误当作Cube计算K块，无法解释实际L0占用。
- 增大K块或打开双缓冲后，希望判断减少的是字节、调用次数还是等待。
- 核任务数相同但耗时不同，或swizzle后的主存流量无法用源码拷贝次数解释。

## 核心物理机理

### 1. 每一级可以使用不同块长

分别定义L1块 `m_b/n_b/k_b`、L0计算块 `m_c/n_c/k_c`、数据字节数 `s_A/s_B/s_C` 及各缓冲版本数 `v`。

对A按MK、B按NK保存的实现，基础容量预算为：

```text
L1  = m_b*k_b*s_A*v_A1 + n_b*k_b*s_B*v_B1 + L1临时/保留区
L0A = m_c*k_c*s_A*v_A0 + L0A临时/保留区
L0B = n_c*k_c*s_B*v_B0 + L0B临时/保留区
L0C = m_c*n_c*s_C*v_C + 其他同时存活累加器
```

还须计入实际布局、对齐和padding；各域分别核对，不能互借容量。具体预算原则复用 [存储预算基础卡](../foundations/writing-paradigms.md)。

例如BF16、L0A/B各64 KiB、各双槽、M/N计算块256时，单槽32 KiB给出 `k_c≤64`；256² FP32结果则占256 KiB。数字用于说明推导，不是所有工具链的通用配置。

### 2. 分清M/N复用与K分组的作用

对一次 `m_c*n_c*k_c` 的BF16输入计算，忽略输出时：

```text
F = 2*m_c*n_c*k_c
D_input = 2*(m_c+n_c)*k_c
F/D_input = m_c*n_c/(m_c+n_c)
```

扩大M/N块可增加输入服务的输出位置；只扩大K块不会直接提高这项比值。

L1 K从64增加到256、L0 K仍为64时，在相同完整K下，源码GM→L1调用轮数减少，每轮消费子步增多；总计算小步和逻辑输入字节不必变化。源码调用数不等于硬件DMA指令数，也不能直接换算加速比。

### 3. 结果留在L0C，避免部分和往返

若一个结果块跨 `q` 个K分组计算，始终片上累加后写一次，只需一次结果输出。假设每组都写回、后续组再读回，则会有 `q` 次写与 `q-1` 次读；两者相差 `2*(q-1)*结果块字节数`。

这是逻辑流量模型，不是某个历史实现的实测行为。扩大结果块也会占用更多L0C，限制跨输出块双缓冲或多累加器。

### 4. 任务数量与缓存局部性分开核查

先计算输出任务数与每核任务数、尾波，再检查任务映射产生的实际地址集合。相同工作量不保证相同缓存行为，持久任务循环也不等于输入常驻L1。

对一段近时任务，分别计算：

- 请求负载：所有任务声明的输入字节总和。
- 唯一地址负载：按batch、操作数及字节范围去重后的输入集合。
- 实际事务：硬件测得的L2/主存读写量。

swizzle可能缩短重复地址的访问距离，使共享L2有机会服务重复请求；它不删除源码拷贝，也不保证并发miss合并、缓存命中或主存只读一次。

## 实现要点与约束

- 仓内例子 `example/gemm/example_batch_gemm.py` 展示BF16 BMK/BNK→FP32、显式L1/L0块、输入多版本、K方向流水和持久任务映射。
- 输入布局必须先确定；右输入已为NK时，转置语义不等于额外GM转置。上游转换成本应计入对应端到端范围。
- 先列逻辑分块与版本，再检查IR/CCE的物理槽偏移、MMAD形状、序言/排空和额外临时区；缓冲版本数并不自动证明时间重叠。
- 固定window的映射须核对完整窗口与尾块。小shape仿真若调整window，必须记录实际候选，不能借其精度结果宣布原特化支持该shape。
- 槽生命周期与输出交接另见 [缓冲与UnitFlag后端核查卡](cube-fixpipe-unitflag-buffer-lifetime.md)。

## 不适用边界

- 更大tile在小矩阵、尾块、资源竞争或任务不足时可能不利；容量合法不等于最优。
- 没有实际事务时，不用逻辑输入字节配主存带宽直接定性瓶颈；共享L2可能改变流量口径。
- 不把单核/部分核trace外推为全核长尾，不把等待跨度当纯搬运服务时间。
- 本卡不提供固定配置的跨设备性能承诺，也不将缺少同协议对照的参数方向归入已证伪反例。

## 验证清单

1. 固定shape、输入/输出dtype、布局、核心数和完整调用边界，独立参考检查全部输出。
2. 按物理存储域预算所有同时存活版本，检查生成代码覆盖的真实读写范围。
3. 分别记录有效FLOPs、逻辑搬运、唯一地址集合、可用的实际缓存/主存事务。
4. 每次只改变要验证的机制；任务数变化、布局转换或输入精度变化不能隐入比较。
5. 小仿真确认覆盖与同步，全核同板同频配对测量确认性能；记录实际warmup与采样，不套用统一预热数。
6. MFU使用完整kernel设备时间与匹配峰值；原理与协议复用 [Roofline与仿真流程](../foundations/roofline-sim-workflow.md)。

## 证据等级

上述容量/流量是代数推导，槽与任务组织由仓内源码及保留生成代码支持。具体tile的全局最优性、缓存事务降低比例及各单项加速幅度仍需目标环境的对照测量，不能由公式或示例配置代替。
