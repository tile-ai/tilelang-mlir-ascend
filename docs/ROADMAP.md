# Operator Harness 路线图

状态：初版规划，随开发逐步补充。

## 1. 项目目标

构建一个帮助 AI 编写、验证和优化算子的 harness。它负责组织任务、提供工具、记录实验并检查验收结果，让用户能够从算子需求出发，得到可复现的代码和验证报告。

项目未来作为独立仓库和工具发布，支持通过 `npx` 获取 CLI，在用户已有的算子项目中初始化和使用。用户不需要克隆 harness 源码才能完成日常操作。

第一版优先复用已有 coding agent 的模型调用和对话能力，建设算子任务、工具和评测流程。首个 agent 宿主与具体实现语言在对应阶段确定。

## 2. 当前状态与开发约定

- 已完成：`harness` 分支初始化，建立 `.gitignore` 和 README。
- 当前阶段：整理路线图；尚未实现 CLI、安装器、工作流或评测系统。
- 开发仅限 `harness` 及其派生分支，不修改其他分支。
- 开发文档统一放在 `docs/`；按当前阶段需要补充，不预先创建空文档和完整目录骨架。
- `.workspace/` 用于中间产物、临时实验、日志和本地备份，不提交、不发布。
- 任务定义、验收规则、最终代码和必要的复现说明进入版本管理。
- 安装版本与配置归属等持久状态使用独立位置，不依赖可清理的实验目录。

本路线图中的命令和目录名称均为规划示意，不代表已经实现或冻结接口。阶段以验收结果推进，暂不承诺日历日期。

### M0：项目与文档起点

建立 README 和本路线图，明确开发范围、临时产物位置以及后续阶段。详细设计只在准备实施对应阶段时编写。

验收条件：新参与者能从 README 找到路线图，区分当前已有能力、下一步工作和远期方向。

### M1：任务与验收契约

选择一个范围小、参考实现清楚的算子作为贯穿后续阶段的示例，确定首个执行后端。定义任务输入、候选代码、执行结果和最终报告之间的关系。

需要明确：

- 算子语义、输入输出、shape、dtype、参考实现和误差容限。
- 编译、正确性和性能分别如何判定，缺少执行环境时如何报告未验证状态。
- 失败、超时和缺少依赖如何表达，哪些情况允许重试。
- 性能测试的设备、预热、同步、重复测量和基线比较方法。

验收条件：同一个任务有明确的通过条件；编译通过不能替代正确性通过，未运行设备测试不能标记为设备验证成功。任务和结果格式允许后续接入其他后端。

### M2：单算子开发与验证闭环

实现最小工具链：准备任务、编译候选、执行验证、测量性能和汇总结果。增加一份开发 skill，指导 agent 使用这些工具完成任务。

先提供可手工调用的函数或 CLI，工具实现可供 agent 和测试复用。实验过程保存到 `.workspace/runs/`，结果关联候选代码版本、命令和环境信息。

验收条件：

- agent 能完成“读取需求 → 编写候选 → 执行验证 → 根据反馈修改 → 交付”的完整过程。
- 错误候选会得到明确的失败反馈；修正后通过任务规定的验证。
- 性能结果能与固定基线比较，并记录性能未达标的情况。
- 使用记录中的命令和环境信息，可以重新验证最终候选。

### M3：CLI、初始化与单宿主接入

建立 npm 包和 CLI 入口，选择一个 agent 宿主作为首个支持对象。提供 `init` 和 `doctor`，把必要的 skills、指令与配置接入用户已有项目。

区分三类内容：harness 自身的开发配置、随包发布的产品资源、用户项目中的配置与产物。建立安装清单，记录版本、受管理文件与配置条目，为升级和卸载提供依据。

验收条件：

- 从打包后的 npm 包初始化一个独立测试项目，无需访问 harness 源码目录。
- 重复初始化不会重复添加配置，用户已有文件和无关配置得到保留。
- `doctor` 能识别缺少的依赖和无效接入，并给出具体修复方向。
- 用户能从该项目通过所选宿主运行 M2 的示例流程。

### M4：实验恢复与执行边界

完善结构化实验记录，明确任务中断、工具失败、超时和恢复后的行为。根据实际事件接入 hooks，自动记录信息或执行检查。

把必须执行的验收条件放入程序逻辑，skills 提供操作方法。限定重试次数与运行预算，定义设备任务的占用、取消和清理方式。需要跨会话恢复的记录应有明确保存与清理约定。

验收条件：

- 中断后能识别最后完成的阶段和当前候选，继续执行时不会误用旧候选的验证结果。
- 失败和超时不会被报告为成功，重试不会无限进行。
- 完成状态只能由满足验收要求的证据产生。
- 配置的分支和执行范围限制在工具实际执行处得到检查。
- 阶段 hook 的注册与触发有实际验证，单独存在脚本不算完成接入。

### M5：独立分发与生命周期

完成升级、卸载、配置迁移、许可证、使用文档和发布流程。明确支持的 Node.js、Python、agent 宿主与后端环境范围。

CLI 的版本更新和已安装资源的更新分别管理。升级时识别用户修改；卸载仅处理本工具拥有的内容。编译器、驱动和设备环境通过明确的准备流程管理。

验收条件：

- 用户可以通过带版本号的 `npx` 命令初始化并运行示例；完成发布后，从发布源再验证一次。
- 发布包包含运行代码和必要资源，不包含 `.workspace/`、本地配置或开发缓存。
- 发布前在独立临时项目中测试安装、重复安装、升级与卸载。
- 升级遇到用户修改时报告冲突并保留原内容；卸载保留用户算子代码与实验结果。
- README 提供环境要求、快速开始、版本固定方法和排障入口。

### M6：按证据扩展

在前述流程稳定后，根据实际使用需求选择扩展项，不要求同时开展：

- 增加算子与边界用例，覆盖不同规模、dtype 和数据布局。
- 增加 agent 宿主、编译后端和远程设备适配。
- 为需要跨工具复用的能力提供 MCP 服务，或接入已有 MCP 服务。
- 在正确性验证之后增加性能优化策略与实验比较。
- 有实际吞吐需求时再引入任务队列、并发和多 agent 协作。

每项扩展需要具体用例、兼容性说明和独立验收条件，验证是否改善任务完成率、复现能力或执行效率。

## 4. 组件与目录的演进原则

| 内容 | 规划位置 | 首次需要的阶段 |
| --- | --- | --- |
| 路线图、契约和设计说明 | `docs/` | M0 |
| 任务与参考实现 | `tasks/` | M1 |
| 任务与结果的数据格式 | `schemas/` | M1 |
| 工作流、工具和评测实现 | `src/` | M2 |
| 对外交付的 skills 与模板 | `assets/` | M2–M3 |
| CLI、安装器、宿主适配 | `src/` 下按职责组织 | M3 |
| npm 包声明与构建配置 | 仓库根目录 | M3 |
| 安装、升级与发布包测试 | `tests/` | M3 起逐步补齐 |
| 配置迁移与发布流程 | 按实际实现添加 | M5 |
| 实验日志、候选和缓存 | `.workspace/` | M2 |

仓库自己的 `AGENTS.md` 和开发 skills 用于开发 harness；交付给用户的内容由 `assets/` 等产品资源提供。用户项目中的具体安装位置由宿主适配决定。

## 6. 如何更新本路线图

当前下一步是 M1：选定首个任务，补充任务和验收契约。实施阶段时再增加相应设计文档，并从本路线图链接过去。

阶段完成后更新状态并附上实现、测试或示例的证据。仅完成设计不标记实现完成；未具备设备验证条件时明确保留该项待验收。

新增需求先归入相应阶段。只有影响当前阶段接口或验收条件的决定需要立即展开，其他内容保留为后续事项。
