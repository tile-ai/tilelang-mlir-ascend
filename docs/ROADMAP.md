# Operator Harness 路线图

状态：首轮工作流试用已完成；下一阶段优先建设候选执行数据契约、MCP 与通用 runner。

## 1. 项目目标

构建一个面向华为昇腾 NPU 的算子生成 harness。首批仅接入 [TileLang](https://github.com/tile-ai/tilelang)，保留语言扩展能力；AscendC 为后续可选扩展。它负责组织任务、提供工具、记录实验并检查验收结果，让用户能够从算子需求出发，得到可复现的代码和验证报告。

默认开发循环为analysis → develop → device-test → analysis：首次analysis分析标杆实现思路，后续通过测试反馈、仿真和流水证据定位当前kernel问题。实卡精度/性能按目标验收；新仿真与流水采集按分析问题选用。仿真和实卡测试均以本地/远程 × host/docker 四种执行组合为目标，逐项适配与验收。

项目未来作为独立仓库和工具发布，支持通过 `npx` 获取 CLI，在用户已有的算子项目中初始化和使用。用户不需要克隆 harness 源码才能完成日常操作。

第一版优先复用已有 coding agent 的模型调用和对话能力，建设算子任务、工具和评测流程。首个 agent 宿主已确定为 Codex，其他运行组件的实现语言在对应阶段确定。

具体背景、任务清单和建议阶段检查见 [需求与工作流](REQUIREMENTS.md)；现有 skills、simulator、Onboard 和 GSD 的检查结果见 [复用计划](REUSE_PLAN.md)。

### M1：任务与验收契约

选择一个范围小、参考实现清楚的算子作为贯穿后续阶段的示例，确定首个芯片/工具链与执行组合。定义任务输入、候选代码、执行结果和最终报告之间的关系。用具体算子对照评估 GSD 整体接入与借鉴阶段机制两种方案。

需要明确：

- 算子语义、输入输出、动态 shape 语义、case 范围、dtype、布局、参考实现、误差容限和外部约束。
- 环境探测、最小编译/运行检查、附加限制及编译与运行位置。
- 独立的精度参考和性能基线，固定输入、测试范围与修改规则。
- 编译、正确性和性能分别如何判定，缺少执行环境时如何报告未验证状态。
- 失败、超时和缺少依赖如何表达，哪些情况允许重试。
- 性能测试的设备、预热、同步、重复测量和基线比较方法。

验收条件：同一个任务有明确的通过条件；编译通过不能替代正确性通过，未运行设备测试不能标记为设备验证成功。阶段检查能阻止缺少证据的推进，候选改变会使相关旧证据失效。任务和结果格式区分语言、执行位置、隔离环境及验证能力。

试运行 TODO（2026-11-02，流程引导改进，非 bug）：初始化遇到环境议题时，显式引导 agent 读取并进入 `harness-prepare-environment`，再通过交互敲定环境细节和准备方式。保留强模型自主调查与推进的能力，复用已有答案；不要把阶段切换变成重复审批。后续单独验证没有下一节点提示时，初始化入口是否仍能自然分流。

### M2：单算子开发与验证闭环

**已完成的试用**：以 MoEPermuteAlignFwdOp 贯穿需求、环境准备、标杆、analysis、develop、device-test 和 automatic 接续。2026-11-03 用户接受工作流及测试环节；已有真实标杆、候选完整输出和性能样本。算子全部性能目标、生产入口验收及通用工具产品化仍未完成。试用范围、结果和改进依据见 [工作流试用总结](workflow-trial.md)。环境恢复与算子进一步调优单独接续，不作为继续观察工作流的前置任务。

已提供标杆建立节点、analysis → develop → device-test → analysis 循环、节点交接契约，以及 torch_npu 采集方法和解析脚本。以下为待设计、实现和验证的工作，按优先顺序推进。

#### 1. MCP 与版本化候选执行契约

确保 develop → test 的算子细节无损传递；MCP 提供发布、读取与执行入口，编译元数据导出、schema、产物身份和执行前检查共同保证完整性，不能只把 Markdown 搬进 MCP。

- 执行包包含语义、shape/dtype/layout/stride、输入输出容量、workspace 大小/对齐/别名/生命周期、阶段依赖与同步。
- 每阶段包含源码/二进制摘要、编译器/目标/配置、入口/ABI/参数顺序、grid/block、mix mode、动态共享/local memory、所需 launch API 和 stream。编译器能够提供的字段自动导出，避免 agent 手抄或猜测；源码尚未编译时明确区分未知对象与已验证对象。
- test 消费同一契约，缺字段、未知版本、摘要不符或后端不支持时返回具体错误；可选、未知与零值明确区分，不静默回退 legacy launch 或 local memory=0。
- flush 等辅助 kernel 使用相同执行契约。结果绑定候选/协议/执行包版本，回传实际 launch 配置和证据索引。

首个验收：以试用中 local memory 32768 信息丢失案例验证“编译端导出 → MCP 传递 → test 消费 → runtime 实参”；故意删除或改错字段应在上板前拒绝。全新上下文 agent 无需聊天补充或重推 ABI 即可消费；schema/后端升级有可检测的兼容边界。

#### 2. 随 harness 交付统一 runner

当前 skill 方法与脚本继续作为验证基础；通用执行工具应复用已经验证的 Onboard/DeepJIT 能力，覆盖普通内核编译、前台提交、精度/采集、状态查询、退出传播、回执与结果回收。可先提供函数或 CLI，再由 MCP 调用，不要求用户机器预装作者个人的上板 skill。

- 用户配置连接、设备、路径和使用约定，不继承作者机器配置；本地/远程 × host/docker 分别适配。没有预装个人 skill 的干净项目也能完成最小编译、运行、比较和回收。
- 运行工具固定私有目录与归档位置，独立保存 SSH/worker/设备作业退出码；避免各节点重复拼接 shell，覆盖只读变量导致退出码遗漏的已见问题。
- 按环境约定执行共享锁和可见性检查，不将某台机器的锁政策普遍化；受锁约束的任务保存本任务独立 receipt，不能依赖下一持锁者可覆盖的共享 metadata。
- 既有授权与有界预算复用，普通编译/JIT不自动触发重复审批；负载未知先有界校验，失败和重试计入额度，状态未知不重投。

验收：真实输入/完整输出/原始采样与实际作业身份对应；两个串行任务可独立核验结束状态，控制端非零退出不会被吞掉，所有写入均在声明范围内。

#### 3. 结构化状态、故障路由与恢复

- 区分请求动作、实际执行范围、节点交付状态、精度/性能判定及外部 job 状态；记录 failure_stage、failure_domain 和缺失能力。
- 工具适配缺失、NPU初始化故障、候选构建/精度/性能失败分别路由；analysis 提出设备对照前有界检查关键接口静态可行性，不强制分析节点执行设备探针。
- 工具在执行前创建 running/checkpoint，自动保存状态查询、配置和原始输出；协调者接收后更新当前候选/最佳候选、STATE、环境可用性与下一步导航，历史归入 runs/EXPERIMENTS。
- 当前故障不追溯改写旧测量；旧 ready 也不能覆盖新初始化失败。跨 skill 的协议/路由表述保持一致，具体入口能力按版本检查。

验收覆盖“已获锁但 aclInit 失败”“节点结束但实验未执行”“控制端断线、状态未知”“用户暂停”及新旧候选混用；恢复仅补齐记录或接续原作业，不重复扣额、派发或测量。

#### 4. 标杆工具与协议验收

- 采样前冻结比较语义、候选资格、输入/seed、计时阶段、统计与分派规则；用户覆盖锁频等要求后固定新协议，执行器不额外增加门槛。首次JIT、预热与正式采样分开。
- 有界调查实现、版本和逐shape资格，区分原版/适配版，保留排除理由；正确性失败不等于更慢，适配参考不能无限扩展成另一个算子开发任务。
- 保留全部样本、失败/无效作业、频率观测范围和排名波动；观测同频不称为锁频，小均值差不称为稳定优势。独立重解析数据、重算分派并核对回执，拒绝不可比结果。

#### M2 验收条件

- 一个真实 TileLang 任务在明确环境中完成构建、全部必选精度与固定协议性能比较，保留未达标和无收益尝试。
- 从记录中的源码/产物、输入、环境和命令可以重新验证候选；当前候选与最佳已验证候选明确分离。
- 全新 agent 能消费执行包并完成测试；基线缺失、身份失效、语义/容限变化不能静默通过。
- 有界任务提交、结束和恢复能由程序契约检查，不依赖主 agent 手工重组所有细节。

独立 AscendC 语言入口不属于本阶段。M2 优先完成设备执行与数据交接；完整执行矩阵、仿真 MCP 和更广泛恢复能力在 M4 扩展。

### M3：CLI、初始化与单宿主接入

建立 npm 包和 CLI 入口，以 Codex 作为首个支持宿主。提供 `init` 和 `doctor`，把必要的 skills、指令与配置接入用户已有项目。

已提前实现 `harness-new-project`、`harness-onboard` 与本地源码安装器，产物统一写入 `.workspace/`，使用方式见 [README](../README.md#使用方式)。这部分只建立需求、计划与接入证据，不代表 npm 分发或 M2 执行闭环完成。

区分三类内容：harness 自身的开发配置、随包发布的产品资源、用户项目中的配置与产物。建立安装清单，记录版本、受管理文件与配置条目，为升级和卸载提供依据。

验收条件：

- 从打包后的 npm 包初始化一个独立测试项目，无需访问 harness 源码目录。
- 重复初始化不会重复添加配置，用户已有文件和无关配置得到保留。
- `doctor` 能识别缺少的依赖和无效接入，并给出具体修复方向。
- 用户能从该项目通过所选宿主运行 M2 的示例流程。

### M4：执行矩阵、仿真与实验恢复

针对仿真与实卡两类执行，分别补齐本地 host、本地 docker、远程 host、远程 docker。语言与执行环境分别适配，按兼容性矩阵验证，不把 SSH 与 Docker 支持混为一项。

在 M2 候选执行契约与设备工具基础上扩展 simulator MCP，提供环境检查、任务提交/状态/取消、产物回收和分析能力。analysis负责首次标杆思路与后续kernel诊断，按需运行流水采集并记录仿真或实卡来源、采集参数与数据完整性；分析用于提出优化假设，收益仍以实卡验证为准。

完善结构化实验记录，明确任务中断、工具失败、超时和恢复后的行为。根据实际事件接入 hooks，自动记录信息或执行检查。

把必须执行的验收条件放入程序逻辑，skills 提供操作方法。限定重试次数与运行预算，定义设备任务的占用、取消和清理方式。需要跨会话恢复的记录应有明确保存与清理约定。

验收条件：

- 中断后能识别最后完成的阶段和当前候选，继续执行时不会误用旧候选的验证结果。
- 失败和超时不会被报告为成功，重试不会无限进行。
- 完成状态只能由满足验收要求的证据产生。
- 配置的分支和执行范围限制在工具实际执行处得到检查。
- 阶段 hook 的注册与触发有实际验证，单独存在脚本不算完成接入。
- 八种执行组合分别完成 TileLang 最小任务验收，按芯片与工具链支持版本记录结果；缺少环境的格子保留待验证状态。
- 仿真 MCP 至少通过一轮真实客户端提交、状态查询和结果回收，并验证失败/取消行为。
- analysis能产生可追溯报告；无须新采集时可用源码/已有证据完成分析，残缺采集不会成为完整性能结论。

### M5：独立分发与生命周期

完成升级、卸载、配置迁移、许可证、使用文档和发布流程。明确支持的 Node.js、Python、agent 宿主与后端环境范围。

发布范围以实际验收矩阵为准。首批目标为 TileLang 与完整执行矩阵；若先发布已验收子集，明确列出限制，未完成的 M2/M4 项目仍保持待完成，不能借发布动作将其关闭。

CLI 的版本更新和已安装资源的更新分别管理。升级时识别用户修改；卸载仅处理本工具拥有的内容。编译器、驱动和设备环境通过明确的准备流程管理。

验收条件：

- 用户可以通过带版本号的 `npx` 命令初始化并运行示例；完成发布后，从发布源再验证一次。
- 发布包包含运行代码和必要资源，不包含 `.workspace/`、本地配置或开发缓存。
- 发布前在独立临时项目中测试安装、重复安装、升级与卸载。
- 升级遇到用户修改时报告冲突并保留原内容；卸载保留用户算子代码与实验结果。
- README 提供环境要求、快速开始、版本固定方法和排障入口。

### M6：按证据扩展

在前述流程稳定后，根据实际使用需求选择扩展项，不要求同时开展：

- 增加算子与边界用例，覆盖不同规模、dtype 和数据布局。
- 按需求评估 AscendC 等语言扩展，以及更多 agent 宿主、芯片/工具链组合和首批矩阵之外的执行适配。
- 扩展仿真 MCP 和其他工具服务；按实际需求决定 Onboard 的 MCP 接口。
- 在正确性验证之后增加性能优化策略与实验比较。
- 有实际吞吐需求时再引入任务队列与并发调度服务；为隔离上下文使用宿主子 agent 的接续流程已提前提供。

每项扩展需要具体用例、兼容性说明和独立验收条件，验证是否改善任务完成率、复现能力或执行效率。
