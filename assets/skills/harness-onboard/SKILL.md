# Harness Onboard

理解已有项目，并明确用户接下来想做什么。与同级 `harness-new-project` 成对提供，共享追问指南和项目记录约定。

## 了解现状

按 [项目管理契约](../harness-new-project/references/project-management.md) 确定工作目录、project_id 和本会话归属。接入对象是已有代码上的开发目标；一个仓库可以对应多个项目，一个项目也可涉及多个仓库。与用户敲定项目名，不因同仓库存在其他项目就合并记录。初查源码可只读，任何开发修改先在项目 repos/ 中准备独立 worktree。

围绕本次目标查阅代码入口、编译与执行方式、参考实现、测试和相关设计。使用可用的代码检索工具，能从文件查清的事实自行查清。梳理有用的发现和来源；尚未运行的测试写成待验证，不把运行命令的存在当成通过记录。

按 [项目契约](../harness-new-project/references/project-contract.md) 同时读取目标仓库的 AGENTS、公开 API/注册方式、贡献指南、lint/CI、打包/测试和 PR/MR 模板，核实其适用范围与版本。记录依赖所需功能和验证入口；检查计划不等于已执行，不在接入时自动运行高成本 CI 或安装依赖。

已有优化记录和测量时，保留其候选与环境关联，提取相关尝试到实验索引，分别标明当前代码和最佳已验证版本。查不到的历史不补写成已完成实验。

把现状简要记录到 `.workspace/<project>/codebase/MAP.md`，重点包括入口与调用关系、现有约束、可复用的测试和需要注意的问题。范围按任务决定，无需逐项写检查报告。只有文档时说明依据来自文档；空项目直接进入新项目的追问步骤。

## 基于现状追问

读取并使用共享的 [追问指南](../harness-new-project/references/questioning.md)。从已有材料和用户后续目标出发，沿回答继续深入，不要求重新介绍整个仓库。

区分现有实现和用户期望。文档、源码与目标有冲突时，先查能查清的部分，再就影响方案的取舍向用户追问。例如只有固定 shape 的示例不足以判断是否支持动态 shape；需要查看相关实现，再澄清本期要支持的输入范围。

已选项目记录中的未决问题继续讨论，新目标补充到原计划中；用户只是重复调用且没有新需求时，说明当前进度与下一步即可。

## 更新计划

首次接入时按项目管理契约调用 projectctl create，建立项目身份和 owner；继续已有项目时核对状态和会话归属。准备独立 worktree 后才开始代码修改，不直接改只读调查的源仓库。

理解收敛后，按共享的 [项目记录](../harness-new-project/references/project-records.md) 直接更新 Markdown。沿用已有决定和人工修改，补充本次的新发现；缺失的记录按需补齐，过时的路径直接修正。

PROJECT 采用 [项目模板](../harness-new-project/assets/templates/project.md)，固定本期开发与交付约定；已有文档按范围补齐身份、规则来源和未决项，不伪造历史检查。后续实测版与发布版通过 DELIVERY 说明差异及验证覆盖。

接入进度、当前候选、已知性能、待决问题和下一步写入 `STATE.md`，无需另写接入摘要。最后简述关键发现、计划变化和下一步。用户有后续分析或调优任务时，按同级 [harness-resume](../harness-resume/SKILL.md) 接续；其中的子 agent 交接方式也适用于较长的现状调查。
