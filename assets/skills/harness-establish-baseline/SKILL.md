# Harness Establish Baseline

把“和谁比、怎么比、在哪个环境比”落实为下游可直接复用的标杆。正确性参考负责定义正确输出，性能标杆负责提供比较时间，两者可以是不同实现；现有环境探针和算子候选都不能自动充当标杆。

## 进入节点

按 [harness-resume](../harness-resume/SKILL.md) 与 [节点契约](../harness-resume/references/node-contract.md) 恢复或建立 TASK。已分配 TASK 的子 agent 只执行本节点，不递归编排。读取需求、用户决定、case、已有参考/标杆和相关结果，明确本次是只调查、建立实测标杆，还是因具体变化更新标杆。

复用已确定的环境和权限。执行时绑定所需 development/device 约定的具体修订、源码/依赖身份和资源额度；只读调查无需伪造运行环境。缺少目标设备身份、编译/输出比较/计时能力或工具入口时，说明具体缺口并建议 [环境准备](../harness-prepare-environment/SKILL.md) 补齐受影响能力，可继续独立调查；不重新选择机器或默认扩大安装、构建与设备预算。使用项目实际可用的执行工具，本 skill 不提供虚构的统一运行命令，也不依赖个人机器上某个私有 skill。

## 明确比较契约

先从规格和已有测试查清语义，只有会改变比较结论的真实选择才向用户追问，回答落到 DECISIONS：

- 必选 case 的 shape、dtype、布局/stride、输入分布、边界行为和全部输出；无序结果、padding、非法输入等按任务定义验证，不能仅比较外形。
- 正确性参考、容限与独立检查方式。用小型可手算样例或数学不变量核对参考；不能让待测实现与标杆互相证明正确。
- 基线实现限制（如必须 AscendC）、来源范围、可用版本、workspace/精度约束和调查/测试预算。“最快”是指定环境与范围内的实测结论，不承诺全局最优。
- 目标倍数的含义、逐 case 或汇总验收、权重及允许退化；使用一个统一实现还是按 case 固定分派。没有明确选择时不事后挑每个 case 的赢家拼成单一实现。
- 完整算子、单 kernel 或端到端计时范围；必要预处理、排序、搬运、同步和后处理是否计入必须对双方一致。

按 [实卡验证协议](../harness-device-test/references/validation-protocol.md) 固定输入/seed、预热、重复采样、重置/缓存、同步、统计量、负载与样本无效判据。TASK 允许本节点创建参考、case 或协议时，先在 run 内保存带摘要的具体版本，再开始受其约束的验证/采样。过程中改变这些条件必须保留旧版并重验受影响结果，不能为了某个实现通过而放宽验收。

## 调查和筛选实现

从用户提供的源码、项目已有基线和目标平台官方实现入口开始，按任务范围继续寻找其他适用仓库、发布版本、特化实现或调优配置。记录来源、revision、入口、构建参数、支持范围与候选状态；不要只因名字类似、版本最新或已有宣传性能就认定是对应算子或最快版本。用户要求最快版本时，调查范围及停止理由必须可复查；只有一个候选可用时如实说明，未测候选不能视为更慢。

逐项核对语义与测量边界。若候选是融合算子或只实现部分功能，记录差异；仅在 TASK 范围内做保持语义的适配，固定适配源码和必要开销。不能截取融合实现的一段耗时冒充完整算子，也不能删除用户要求的输出。不可比、缺包、编译失败或超预算的候选保留原因，不静默丢弃。

选择规则和比较协议在看到性能结果前固定。按约定规则选择统一实现，或固定可复现的逐 case 分派表；并列/噪声不足以区分时报告不确定性，不以最快单次样本决胜。

## 取得正确性和性能证据

在 device 约定和本次预算内，使用实际工具构建每个纳入测量的候选，关联源码、适配、产物、入口与 launch。对每个候选先完成其拟承担的全部必选 case 输出比较，再进行该范围常规性能采样；统一实现应覆盖完整 case 集，逐 case 分派的最终组合也必须覆盖全部必选 case。失败实现不得因快而入选。

所有参与比较的实现使用相同的输入、语义、计时范围、协议和可比环境；保留原始样本、统计和失败/排除项。旧测量只有身份及比较条件匹配才可复用。文档数字、仿真 cycles、环境样例耗时或不同机器结果不能直接成为本次实卡标杆。

记录候选集内的选择依据和残余不确定性；预算耗尽、缺失 case 或不可比测量只能形成部分结果，不能宣布已找到最快标杆。后台作业/超时/断线按共用契约保存身份、回收与结算，不重投状态未知的作业。原标杆在新版本验收前保留，不能用未验证替代品覆盖。

## 固定交付与推荐下一步

使用 [BASELINE 模板](assets/templates/baseline.md)，在本 run 输出 `BASELINE.md`，连同 RESULT、可重建参考/适配代码、case/协议快照、构建与运行命令、原始输出/样本及日志交付。`readiness: ready` 仅表示该修订满足声明的全部使用条件，不表示目标算子达标；只调查可完成本次 TASK，但标杆保持 draft。没有全部必需证据时，明确缺口与可执行的后续动作。

协调者检查后，在 `.workspace/BASELINE.md` 发布轻量索引，指向本 run 的不可变基线记录与证据，并更新 STATE/EXPERIMENTS；子 agent 不直接发布。下游 TASK 必须将索引解析为确切的 baseline ID/修订/摘要，不在执行中跟随可变指针。变更参考/case、来源/构建、执行环境或测量协议时，先判断影响范围，保留旧版并更新受影响的基线证据。

最终回复与 RESULT 都应给出**一个主推荐**：具体节点/skill、原因与证据、依赖或缺口、完成/停止条件。标杆 ready 后通常推荐 [harness-analysis](../harness-analysis/SKILL.md)，读取冻结标杆的实现与测量边界，形成首次开发方案；已有分析时按 [统一路由](../harness-resume/references/next-action.md) 检查受影响部分，复用仍适用的结论。环境不足则推荐 prepare-environment 的具体补齐动作。用户要求本节点后停止时仍给建议，但不执行下一节点。
