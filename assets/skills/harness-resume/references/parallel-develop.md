# 多方案并行开发

协调者可以把多个已接收 analysis 的独立优化方案分配给多个 develop 执行者。每个 develop 都实现并测试自身候选。并行只改变派发方式，不改变正确性、性能、环境许可或验收标准；本契约由宿主 agent 执行，searchctl 只登记与校验，不自动启动 agent 或设备作业。

## 准备比较批次

1. 接收 analysis RESULT，确认每个方案的具体改动、预期收益、风险、验证计划和可写范围。一个 analysis 也可以输出带 plan_id 的多个方案；多个成员可引用同一 analysis_run，TASK 另固定各自 plan_id。互相依赖的方案顺序实施，不强行并行。各方案必须基于同一个候选（初版允许 null）及同一需求、基线、case、协议和环境比较约定。分析曾绑定其他版本时先确认适用性，必要时重新分析，不静默换输入。
2. 为每个成员通过 projectctl 的 add-repo 建立独立 repo_id/worktree/branch。同一 Git 来源可以有多个注册 worktree。依赖源码需要修改或构建写入时也隔离；共享依赖只读。父候选包含未提交补丁/未跟踪文件时，将确切快照恢复到每个 worktree 并核对摘要，不能只 checkout 父 HEAD。禁止多个执行者共用一个源码目录，即使计划改不同文件。
3. 生成唯一 run_id、候选命名空间和 `.workspace/<project>/runs/<run-id>/TASK.md`。固定分析 RESULT、可写 repo_ids 与具体文件、共同输入快照、预期输出、development/device 绑定、资源预留、修复上限、远端目录及独立 build/JIT/cache。TASK/RESULT 保留 batch_id、analysis_run；批次登记不会替你补齐 TASK。
4. 协调者串行预留资源与控制步数，再用 [批次操作模板](../assets/templates/develop-batch.json) 提交 `searchctl apply`。inputs 为 workspace_root 相对路径，helper 保存内容摘要；不测性能时 baseline/protocol 仍指向已固定的范围说明文件，不填不存在的路径。candidate_id 是共同父候选或 null。单个成员列出全部可写源码 repo_ids，不列共享只读依赖。

`develop-batch` 原子登记至少两个 develop run：校验项目 owner/生命周期、已接收且 completed 的适用 analysis、候选/策略归属、open 节点、独立 TASK 路径，以及已注册且分支正确的非重叠 worktree。不同成员允许属于不同搜索节点，不改 current_node。普通 run 仍限当前节点，普通 develop 不能与其他未接收 run 并行；仅同一节点的只读 analysis 可并行登记；有任何尚未接收且未安全关闭的 run 时不能启动新批次；批次仍有在途成员时不能新增普通 run 或切换策略。先准备分析、再一次登记批次；不能通过普通 run 操作冒充跨策略并行。

helper 校验身份、摘要和 worktree 隔离；协调者仍须检查分析方案是否适用共同输入、TASK 与批次快照是否一致、文件白名单/远端目录是否独占、预算是否足够。它不是任意 shell 写入的沙箱，也不是设备锁或性能评选器。

## 派发与设备使用

存在宿主子 agent 能力且资源足够时并行派发；默认最多 2 个 develop 执行者，可按用户约定/宿主上限调整，不超过剩余控制步骤与资源额度。无工具或额度不足以并行时明确采用顺序执行；不为缺少并行工具阻塞任务，也不声称发生了并行。

每个成员单独计一个控制步骤，N 个成员预留 N 步。分配设备额度与等锁时间各自受已有约定限制；不因为打包成一个批次只计一步。准备后未派发的成员保留为 prepared，恢复核对请求身份后派发，不登记第二份任务。

CPU 编译可在资源允许时并行。同一物理设备/共享资源上的精度、性能作业按环境约定排队，性能计时不得互相争抢同一资源；不同设备只有已明确独立资源分配、负载限制且比较条件一致时才并行。不得为了兄弟任务修改共享安装或释放别人的锁。所有成员使用已冻结环境，不自行改核数、协议或基线。

每次派发前保存 step/run/request 意图，返回后补 agent ID。子 agent 只接收 workspace_root 与 TASK 路径，不继承聊天；只能写所属 run 和 worktree，不能修改兄弟任务或共享记录。每个成员在自己的修复预算内实现、冻结候选、精度验证、性能测量，再交付 RESULT。相同失败无新依据不得重试。

## 接收、暂停与恢复

- 成员可以乱序完成。协调者逐份核对实际候选、输入、判定、样本/日志、作业和额度，再串行登记候选并 accept；一个成员精度失败或存在实现问题时仍留在自身 develop 修复，不得 accept；其他成员可以独立接收。失败不抹掉兄弟结果，也不自动取消兄弟任务。只有精度通过、有效性能及思路归因齐全的退化结果才可接收并交回 analysis；接收不等于成为最佳。
- 只有全部成员都接收或按执行控制契约安全关闭后才选择策略/新开批次。不可比的结果保留，但不能按加速比排序；补测属于新任务并单独占步。最佳候选按共同验收规则决定，不以先完成或某一个 case 最快作为胜出依据。
- 直接选择一个成员的确切候选无需合并兄弟改动。若集成多方案，先保存各自证据，再为集成产生新候选，在 develop 中重新执行受影响检查与必选精度/性能。不能把两份 pass 拼成合并版本的 pass。
- 暂停/撤权立即停止新增派发，通知所有执行者在安全检查点停止新操作。AUTOMATIC 保存全部 in_flight_steps（包括 prepared），而非只保留最后一个 run；unknown job 仍占用原预留，不重投。
- automatic 转 next 时停止新增派发；指定成员则只允许它完成原有界动作，其他成员停在安全检查点。未指定时全部成员停在安全检查点并接收已完成结果，不把整批算作一个新步骤。后续 next 明确选择一个待续成员；恢复 automatic 仍需用户明确请求。
- 接续先核对每个成员的派发意图、执行者、原 job 与检查点。未派发任务可在原步骤内启动；不确定是否已派发时保留 blocked。接管协调者不重启仍活跃的成员。终态 RESULT 不改写，补充任务另建 run；未终态成员仍按同一 TASK 恢复。

范围内失败继续原节点修复；需要改范围、放弃或补充终态交付时，按 [安全关闭](execution-control.md) 保留原记录并关联后继任务。关闭的 analysis 不能充当已接收分析。
