# Harness 工作流改进备忘

状态：下列条目待讨论与实施。已落实的项目隔离、会话归属与冻结/归档/恢复统一见 [多项目管理](projects/design.md)；交付检查前移与项目模板见 [项目契约](../assets/skills/harness-new-project/references/project-contract.md)，均不再作为本备忘待办。标杆来源入口、调查记录与复查流程已落实到 [标杆节点](../assets/skills/harness-establish-baseline/SKILL.md)，原问题 3 不再列为待办。其余建议不改变现行验收规则或授权范围。

## 目的与判断

依据 `harness-engineering` 的评审框架，从评测冻结、可编辑范围、持久记录、搜索纪律、恢复和交付权限审视现有工作流。

现有 harness 已能组织完整的算子开发，具备候选与最佳已验证候选分离、冻结输入、失败保留、未知作业不重投，以及 hot/cooled 修订和审批绑定等基础。主要改进方向是把仍由协调 agent 手工承担的检查，逐步变成可验证的工具行为。

本备忘与 [M2 路线图](ROADMAP.md) 中的执行契约、统一 runner 和结构化状态建设衔接。具体任务记录、设备配置和测量数据保留在用户项目的 `.workspace/`，不写入通用产品文档。

## 1. 评测冻结与结果验收：最高优先级

现有 [节点契约](../assets/skills/harness-resume/references/node-contract.md) 要求冻结参考、case、协议和环境身份，禁止候选修复节点静默改变验收条件。需要进一步落实到执行前检查与结果接收。

| 对象类别 | 内容 | 建议行为 |
| --- | --- | --- |
| 冻结 | 正确性参考、case、容限、计时口径、标杆选择规则 | 记录实际依赖文件的身份，执行前后核对；变更产生新修订 |
| 可编辑 | 候选源码、获准修改的配置 | 声明可写范围，保留可恢复快照 |
| 追加记录 | 尝试、失败、接收、资源结算 | 保留历史，禁止覆盖终态；更正以新记录关联旧记录 |
| 用户控制 | 验收标准变更、推送、合并、破坏性操作 | 引用有效授权及其作用域；仅对真实缺口补问 |

`searchctl` 当前校验登记文件的摘要、身份和关系；它对 develop 增加了精度声明、性能归因与证据摘要的接收检查，但不递归解析全部评测依赖、不重算逐 case 结果或验证资源余额。`accept` 登记终态结果不等于该结果已满足算子验收。这是其 [账本边界](../assets/skills/harness-resume/references/search-knowledge.md)，后续验收工具应补齐边界，而非直接将账本登记视为通过。

建议建立显式的评测依赖清单与验收记录：必选 case、结果、参考与候选身份、测量协议和原始证据对应后，才能晋升最佳已验证候选。程序校验与隔离可写范围分别设计，文件摘要本身不能阻止有写权限的执行者同时修改文件和摘要。

测试框架修复应区分“实现修复”与“验收语义改变”。两者都保留前后版本及原因，明确受影响的结果；不得通过放宽条件使当前候选自行通过。评测器变更时，对适用的已知正确与错误样例同时运行旧、新评测器并解释判定差异。

## 2. 稳定测试执行链：最高优先级

将节点反复拼接的环境检查、作业提交、采样和回收收敛到统一 runner。推荐顺序为：

```text
CPU 预检 → 环境身份检查 → 按约定获取设备
→ 最小执行 → 完整精度 → 性能采样 → 回执与退出核验
```

- 导入、配置解析、源码身份采集和测试收集等能在 CPU 验证的内容先验证。
- 初始化探针、张量操作、kernel 和 profiler 分别声明能力需求；是否获取锁由环境约定决定，不统一套用某台机器的政策。
- 区分等待锁、已持锁等待设备、实际执行、结束和状态未知；报告包含观测时间及来源。
- 保存提交意图、请求与作业身份、独立回执、各层退出码和取消入口；重连先恢复原作业。
- 尽早用真实公开 Op、adapter、缓存与输出生命周期做最小验证。专用 runner 的证据明确覆盖范围，不能自动等同生产调用链验证。
- 区分候选故障、测试基础设施故障和外部测量无效，按证据决定修复、重试或停止。

这些工作落实 [M2 的执行工具与恢复要求](ROADMAP.md)，无需先建成完整 MCP 或后台调度服务。

## 4. 搜索选择、淘汰与简化

[搜索树](search/design.md) 已能记录策略、候选谱系和失败分支。后续补充实验选择规则，让历史记录真正影响下一步：

1. 较大实验前比较已有成功、失败和无收益尝试，说明本次改变的机制、适用条件和新增证据。
2. 写明预期瓶颈、可证伪的 case，以及保留、淘汰或返回旧候选的条件。
3. 分析完整调用链中的重复工作、独立 launch、并行度、数据搬运、计算和同步，不只调整局部参数。
4. 多个优化叠加后，在预算内选择有价值的移除对照；收益相当时优先保留更简单的方案。
5. 替代旧实现时检查分派、缓存和调用入口；保留历史源码与结果不意味着继续保留无用的运行路径。

hot/cooled 可逐步增加稳定的机制标识、归属、激活条件、行为变化、证据和失败模式，用于查重和复用。知识应表达有条件的经验，不将满核、融合或多缓冲写成无条件要求。机制字段如何演进及兼容旧记录，另行设计。

## 5. 状态维度与持久事件

节点是否结束、精度是否通过、性能是否达标、证据是否完整、外部作业是否退出、协调者是否接收，应分别表达。避免用一个混合状态承载这些不同结论。

建议在既有契约上增加结构化检查，明确状态字段与合法转换。旧记录通过兼容读取或显式迁移接入，保留原文与未知项，不改写历史结论。

接收、资源预留与结算、候选晋升和撤回应有稳定事件身份。重复恢复只补未完成动作，不能重复扣额或提交。可沿用搜索工具的事件设计，将 STATE 等摘要生成或校验为这些事实的视图，避免增加第二套互相漂移的账本。

监控默认只读，报告最佳候选、在途作业、过期证据、最后来源复查和下一步，并引用记录或实时查询。节点级暂停与系统故障停滞的自动路由仍待落实；项目生命周期按项目管理契约执行。

## 建议实施顺序与验收场景

首个里程碑聚焦“工具能够阻止错误推进”，先定义小范围结构化契约与验证入口，再扩展 runner 和搜索纪律。

| 顺序 | 范围 | 验收场景 |
| --- | --- | --- |
| 1 | 冻结评测依赖与结果接收 | 评测文件改变、缺少必选 case、将旧候选证据用于新候选时拒绝晋升；完整匹配的结果可以接收 |
| 2 | 作业身份与恢复 | 提交响应丢失后不重投；重复接收不重复结算；暂停后停止新增动作并保留恢复入口 |
| 3 | 稳定 runner 与真实 Op 入口 | CPU 可发现的脚本错误提前暴露；持锁等待与实际执行可区分；断线后恢复原作业并核验回执 |
| 4 | 搜索与简化 | 重复策略说明新增依据；叠加优化可做有界移除对照 |

每项同时准备一个应通过的样例和一个应拒绝的样例。程序行为测试、工作流演练和算子实卡验证分别报告，不互相替代。

实施前仍需确定结构化格式、与现有 Markdown/搜索账本的兼容方式，以及 runner 首批支持的环境范围。本备忘不要求现在启动实验、迁移旧记录或修改已发布技能。
