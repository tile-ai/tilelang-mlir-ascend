# 实现节点内的设备验证

port-baseline 与 develop 复用本方法及采集脚本，编写后在同一节点内验证。下文 develop 的优化退化归因仅用于优化迭代；port-baseline 按其 skill 的初版接收规则执行，允许已验证初版暂未达性能目标。

读取 `.workspace/<project>/STATE.md`、任务契约、候选与 [证据记录](../../harness-resume/references/execution-records.md)，使用 TASK 固定的 **device 专属约定快照**；实时 ENVIRONMENT 索引只核对漂移/撤权，不替换本次绑定。按 [环境复用规则](../../harness-prepare-environment/references/environment-contract.md) 检查必需能力、身份、预算与设备队列/锁，沿用已确定的连接、容器和限制，不重新问整套环境。

仿真或仅开发环境的许可不能授权设备操作。缺少上板约定或必要能力时，在 RESULT 提出对应缺口，由主 agent 派发环境准备；不能静默改用另一环境。默认按约定串行测量共享设备，发现忙时执行约定的有限等待或报告 blocked。

相对性能验收前读取 TASK 固定的 BASELINE ID/修订/摘要，检查其 ready 状态、case、来源/产物、环境和协议是否适用；无可用标杆时建议 [harness-establish-baseline](../../harness-establish-baseline/SKILL.md)。本节点可按固定协议复测同一标杆，不自行重新选择或改写它。仅精度或用户约定的绝对性能目标不强制建立相对性能标杆。

## 绑定待测产物

正式验收前核对 PROJECT 固定的检查计划与候选 PRECHECK：检查范围、源码/规则身份必须适用。明确的 API、导入或测试收集故障，在 implement-and-validate 的修复额度内处理；verify-only/collect-only 保留缺口并交回协调者；若 TASK 指定有界设备诊断则按其范围执行，缺失的发布条件仍保留。必需证据与诊断附件按 [项目契约](../../harness-new-project/references/project-contract.md) 区分，不能自行追加必需项或将失败项降级。

核对完整候选快照、任务/参考/case/协议版本、lowering 与编译链、目标架构、入口和 launch。必要编译在上板约定指定的位置进行；复用已有二进制前检查身份和兼容性。检查本次运行的代码确实来自该候选，不能仅信缓存文件名或 Git HEAD。

优先适配项目已验证的 Onboard/DeepJIT 或现有测试命令；从其实际接口查参数，不臆造统一 CLI。远程模式记录本地 lowering 与远端构建/执行两段信息。检查产物传输摘要、退出状态与输出回收；SSH 请求成功不等于设备执行成功。

## 性能工具与节点职责

任务要求 MFU 时，使用 [ascend-mfu](../../ascend-mfu/SKILL.md) 从本次协议的完整 kernel 设备耗时和有效 Cube 运算量计算，随结果保存输入及计算输出；这项离线计算不增加设备运行次数。主要性能比较仍使用绑定协议的耗时指标。

采用 `torch_npu.profiler` 测量时，直接执行 [采集方法](torch-npu-measurement.md)：在实际执行 NPU kernel 的进程中包围一次完整调用，保存原始 trace，并按绑定协议统计。配套 [采样脚本](../scripts/torch_npu_measure.py) 和 [设备区间解析器](../scripts/profile_parser.py) 提供确定性的采集与汇总；先核对脚本支持的协议与本次 TASK 一致。脚本不启动远端、不分配设备许可，也不替代完整调用的覆盖核查。

本节点负责在私有运行目录编写算子调用适配、连接已有 profiler、配置协议参数和汇总数据。缺 benchmark 脚本、多阶段入口或结果解析接线属于本节点工具工作；在既有权限和预算内先完成适配及小 case 采集检查，不能仅因“尚未实现/验证”返回 prepare-environment。只有实际 SDK、依赖、设备权限或采集接口故障且超出本节点修复范围时，才携证据建议环境准备。不能把某次外部进程冲突推断为环境没有采集能力。

上传入口同时核对内容摘要和执行权限。候选编译/运行/精度失败与测试准备错误分别处理：尚未提交设备的可修复路径、权限、脚本调用错误，在原范围内修正后继续，保留每次失败文件，不自动追加设备重试。按后端容器/guard/job 证据标 submitted/queued；正常排队到约定上限，不因暂时无输出提前报 blocked。断线先核对真实进程与原作业，不能仅凭工具 session 消失判定设备已停止。

## 先精度，再常规性能

依据 [实卡验证协议](validation-protocol.md) 对全部必选 case 比较全部输出。未执行、缺输出、超时、运行时错误分别保留，不能只凭退出码标 pass。失败时停止该候选的常规性能验收，保存反例与最大误差位置，保存当前尝试；必须在本 develop 内诊断并修复，再冻结新候选，重验全部必选精度。精度失败不允许节点接收，也不能作为正常交接送往 analysis；无权限修改、预算耗尽或环境阻塞时保存未验收检查点，不自行加额。verify-only/collect-only 不擅自修改候选，所需修复范围先交协调者处理。

仅当本次任务包含性能验收、全部必选精度通过且身份未变化，预算、许可和计时能力均满足时，按固定协议执行基线与候选的预热、同步、重复采样和统计，保存原始样本与逐 case 对比。用户只要求精度时到此收尾，性能记 not_run。性能基线本身也须满足相同语义和精度要求。记录设备/环境负载和测量范围；无法取得可比样本就报告性能未验证，不输出伪加速比。

若绑定协议使用 profiler 的设备记录作为性能指标，profiling 就是本次性能测量方式，不另设一个尚不存在的“常规计时”前置条件。不要把采集进程墙钟当设备耗时。额外的流水指标/诊断 profiling 是另一范围，需相应任务和预算；采集失败不抹掉已有精度证据。

## 分析数据交付

完成精度与正式性能后，按 TASK 诊断计划执行 [上板流水与指标采集](onboard-diagnostics.md)，生成本候选 ANALYSIS_DATA。普通性能优化任务默认包含代表性/退化 case 的分析数据；实际指标按工具/芯片能力选择，不做未授权的全量采集。已有适用数据可引用并解释身份一致性；只支持部分指标时保留覆盖边界。必需项缺失不能接收，未要求的可选项不增加验收门槛。

## 结果与恢复

保存任务状态、输出比较、原始样本、环境快照、命令和日志；分别判定精度、性能目标、采集完整性。保留慢的 case、精度失败与未运行项。超时或断线先查原作业，确认结束/取消和清理后才考虑预算内重试；不能盲目再提交。

独立保存 controller、SSH/worker、guard 的退出码及本作业私有 receipt；入口必须传播非零退出或显式返回失败，不能用 controller=0 覆盖 guard 冲突。guard 非零、receipt 缺失、冲突或观察丢失时性能 invalid，保留原始采样；按任务约定决定是否有额度再测，不改规则忽略冲突。退出码的采集与最终 receipt 验收由外层执行入口完成，不能在 guard 尚未结束时宣称性能有效。

按 RESULT 模板写本次结果，由主 agent 接收并更新实验记录。所有必选 case 达标才宣称目标达成；预算耗尽交付当前最好证据与差距。候选修改后旧通过标记不适用于新候选。

精度通过后，性能退化先按 [develop 接收规则](../SKILL.md#接收与下一步) 区分思路与实现：实现问题在节点内修复并重验；原因不明或测量无效留在节点内诊断。只有实现符合方案、证据支持思路问题时，才将退化现象、逐 case 原始结果与归因直接交给下一 analysis，形成 `analysis → develop → analysis` 循环。若本次仅为 analysis 请求的实卡采集，交回原分析问题，不自动修改候选。目标已达成时推荐结束/交付；用户要求停止或预算不足时记录边界，不为循环新增任务。

启用搜索树时，沿用 TASK 的 `search_node_id`，在 RESULT（以及 develop 生成的候选清单）保留同一归属；阶段执行者不自行切换策略节点。将可复用发现与证据交给协调者归入关联节点的 hot，区分观测、假设和结论。见 [搜索与知识](../../harness-resume/references/search-knowledge.md)。
