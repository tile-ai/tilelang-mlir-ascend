# 迁移场景方法论：源算子解读、硬件耦合性判定与 NPU 算法重设计

> 迁移类任务（scenario=migration，含 harness / plain 子模式）的 Stage 1 **必须**按本章方法执行。
>
> 核心思想：**先彻底读懂源算子（语义 / 算法 / 优化手段），再判定实现算法与优化手段是否硬件强相关、能否用在 NPU 上；不能用的，基于 NPU 硬件能力重新设计算法**。迁移不是"逐 API 语法翻译"，严禁跳过解读直接改写代码。

## 1. 总体框架

迁移设计分两步走：**三问解读 → 耦合性判定与重设计**。

```
源算子代码（GPU 实现）
   │
   ▼ 第一问：算子的语义是什么？（What —— 必须保持的部分）
   ▼ 第二问：实现算法是什么？（How —— 计算步骤/数据流/并行结构）
   ▼ 第三问：用了哪些优化手段？（Why fast —— 每项依赖什么硬件特性）
   │
   ▼ 硬件耦合性判定：算法和优化手段硬件强相关吗？能用在 NPU 上吗？
   │
   ├─ 保留        （语义层、纯数学算法步骤、NPU 直接支持的结构）
   ├─ 等价替换    （NPU 有等价硬件能力，按映射表替换）
   ├─ 重新设计    （NPU 无等价能力，按 NPU 约束设计新算法）→ §6
   └─ 舍弃        （NPU 上无意义或有害，说明理由）
   │
   ▼
NPU 侧设计方案（DESIGN.md §1–§11 以此为输入；§0 记录全过程）
```

产出落到 `DESIGN.md` §0（0.1–0.7），并作为后续所有章节（编程模式、API 映射、内存规划、Tiling、循环、同步、验证）的决策依据。

## 2. 第一问：源算子语义是什么（What）

语义 = 迁移中**必须原样保持**的部分。语义解读错误会让后续一切工作失去意义。

### 2.1 必须解读的语义要素

| 要素 | 说明 | 常见坑 |
|------|------|--------|
| 数学语义 | 输入 → 输出的数学映射（公式或文字描述） | 只看函数名臆测语义，忽略实际计算 |
| I/O 契约 | shape、dtype、layout（转置/连续性）、动态轴、是否 in-place | 输出 layout 与输入不同（如输出是转置布局）；输出 shape 需显式确认（迁移必需字段） |
| 规约语义 | 规约轴、keepdim、**累加顺序** | 累加顺序影响 fp16/bf16 数值；NPU 重设计改变并行度时会改变累加分组 |
| dtype 语义 | 中间计算精度、提升/截断规则 | 源码 fp32 累加 + fp16 输出 ≠ 全 fp16 计算；exp/sum 的中间 dtype 必须核对 |
| 边界语义 | nan/inf 传播、空维度、非整除 shape、极值 | softmax 空轴、0-size 维度、`M < block_M` |
| host 侧语义 | 预处理/后处理是否属于算子契约 | im2col 是**实现手段**而非语义；NPU 侧可换实现，但输出必须等价 |

### 2.2 语义解读的完成标准

> **能写出与源算子数值一致的 golden 函数（PyTorch 参考实现），语义解读才算完成。**

- golden 的唯一依据是本节解读的语义（优先移植源仓的参考实现/测试基准），**不是** NPU 算法——保证验证独立性。
- 语义要素表逐项有结论，无法从源码确定的标注「待确认」并说明。

## 3. 第二问：实现算法是什么（How）

算法 = 源码**实际怎么算**：步骤分解、数据流、循环与并行结构。算法层解读回答"每个计算语句在做什么、数据怎么流动"。

### 3.1 源码结构化阅读协议（按顺序执行）

1. **入口签名**：`@tilelang.jit` 函数的参数列表与 shape 推断逻辑 → I/O 契约与 host 侧维度计算。
2. **Kernel 结构**：`T.Kernel(...)` 维度（一维/三维）、block 数计算 → 并行任务划分。
3. **计算原语**：逐个读 `@T.prim_func`（TIR 原语函数）→ 每个函数实现哪一步计算，用了哪些 API（`T.gemm`、`T.reduce_sum`、算术符号等）。
4. **内存分配**：`T.alloc_shared` / `T.alloc_fragment` / `T.alloc_local` 的层级与大小 → 中间数据放哪、复用关系。
5. **循环与调度**：`T.Parallel` / `T.serial` / `T.Pipelined` / unroll → 调度结构与流水。
6. **host 侧逻辑**：kernel 调用前后的 Python 代码 → 预处理（im2col、reshape、cast）、后处理（crop、transpose）。
7. **编译配置**：`pass_configs`、环境变量 → 编译器行为（可能影响实际执行，如自动流水）。

### 3.2 算法解读产出（→ DESIGN.md §0.3）

- **计算步骤分解表**：步骤 | 计算 | 输入 | 输出 | 对应语义公式的哪部分。
- **数据流图**（源硬件视角）：`GM → SMEM → register → ... → GM`，标注每次搬运与 layout 变换。
- **循环与并行结构**：grid/block/thread（或 block/thread）两级划分、循环边界、分块大小。
- **host 侧逻辑**：属于算子调用的预处理/后处理清单。

### 3.3 完成标准

- 源码中**每个计算语句**都能归入某个步骤（无遗漏）。
- 每个步骤都能追溯到语义公式的一部分（无臆造步骤）。
- 数据流图覆盖全部 buffer，无来源不明的数据。

## 4. 第三问：用了哪些优化手段（Why fast）

优化手段解读回答"源实现为什么快"。**识别不出来 ≠ 不存在**——未识别的优化会被静默丢弃，导致迁移后性能回退且无法追溯。

### 4.1 GPU TileLang 常见优化手段识别清单

| 优化手段 | 典型代码特征 | 目的 | 依赖的源硬件特性 | 初判 |
|----------|-------------|------|-----------------|------|
| SMEM tiling | `alloc_shared` + 分块 `T.copy` | 减少 GM 重复访问 | shared memory | 硬件强相关 |
| coalesced 访问 | 尾轴连续读写 | 访存带宽 | memory coalescing | 硬件强相关 |
| Tensor Core / mma | `T.gemm` / mma fragment | 矩阵算力 | tensor core | 硬件强相关（NPU 有 Cube 等价） |
| warp shuffle 归约 | shuffle / intra-warp reduce | 低延迟跨线程通信 | warp（32 线程） | 硬件强相关 |
| 异步搬运 / 多级流水 | `cp.async`、`T.Pipelined` | 访存计算重叠 | 异步拷贝引擎 | 硬件强相关（NPU 有 MTE 等价） |
| double buffer | 双 buffer 交替 | 流水不 stall | — | 模式可移植 |
| swizzle / 布局重排 | index 重排、pad | 消 bank conflict | SMEM bank 结构 | 硬件强相关（NPU 不适用） |
| register tiling / 累加 | fragment 累加、寄存器分块 | 数据驻留寄存器 | 大寄存器堆 | 硬件强相关 |
| persistent kernel | block 常驻循环处理任务 | 消 kernel 启动开销 | — | 模式可移植 |
| fused epilogue | 归约/激活融合进主循环 | 消中间写回 | — | 模式可移植 |
| online 算法（如 online softmax） | 分块局部 max/sum 增量更新 | 消 O(N) 中间缓冲 | **无**（纯算法层） | **可移植** |
| 向量化访存 | 连续多元素一次读写 | 带宽 | — | 模式可移植 |

### 4.2 区分「算法层优化」与「实现层优化」

- **算法层优化**（online softmax、分块累加、数学恒等变形如 `exp(x-max)` 稳定化）：不依赖具体硬件，**通常可移植**，优先保留。
- **实现层优化**（布局、并行结构、搬运调度、存储层级使用）：绑定源硬件组织方式，**通常需等价替换或重设计**。

## 5. 硬件耦合性判定：能用在 NPU 上吗

### 5.1 三层判定模型

| 层 | 内容 | 默认判定 |
|----|------|---------|
| **语义层** | 数学映射、I/O 契约、边界语义、精度语义 | **永远保留**（不可妥协） |
| **算法层** | 步骤分解、数据流结构、分块累加策略 | 逐项判定：纯数学顺序 → 保留；依赖源硬件布局/并行假设 → 按优化层处理 |
| **优化层** | 布局技巧、并行组织、搬运调度、存储层级 | 逐项判定：多数需等价替换或重设计 |

### 5.2 四态处置

| 处置 | 含义 | 适用条件 |
|------|------|---------|
| **保留** | 原样沿用 | 语义层；纯数学算法步骤；NPU 直接支持的结构（如 double buffer、persistent 模式） |
| **等价替换** | 换成 NPU 等价能力，性能意图不变 | 优化层中 NPU 有对应硬件能力（查 §5.3 映射表） |
| **重新设计** | NPU 无等价能力，按 NPU 约束设计新方案 | 无等价能力且该能力影响性能/正确性 → 走 §6 重设计 |
| **舍弃** | 不迁移该项 | NPU 上无意义、无必要或有害；**必须写明理由**（否则性能回退无法追溯） |

### 5.3 GPU → Ascend NPU 能力映射表（等价替换速查）

| GPU / 通用概念 | Ascend NPU 等价能力 | 处置建议 | 注意事项 |
|----------------|--------------------|---------|----------|
| shared memory | L1（Cube 输入）/ UB（Vector 数据） | 等价替换 | 容量与对齐不同：L1 512KB、UB 192KB、32B 对齐 |
| Tensor Core mma | Cube 单元（`T.gemm` + L0A/L0B/L0C） | 等价替换 | 分形限制 M≥16 / N≥16 / K≥32；L0C 128KB；NZ 布局 |
| warp shuffle 归约 | Vector 归约（`T.reduce_sum/max/min`） | **重新设计** | 并行层级不同：warp 32 线程内 shuffle → 向量整行归约，需重排归约策略 |
| cp.async / 多级异步流水 | `T.Pipelined` + MTE 异步搬运 | 等价替换 | num_stages 需按 UB/L1 容量重新计算 |
| double buffer | 多 buffer 交替 | 等价替换 | — |
| swizzle 防 bank conflict | NZ 分形布局（`load_nd2nz` / 框架处理） | **舍弃** | NPU 无 SMEM bank conflict，手动 swizzle 无意义 |
| block × thread 两级并行 | block 级任务划分 + 向量化元素并行 | **重新设计** | 本项目 `T.Kernel` 只接受一维 block 数 |
| register 累加 | L0C 累加器（fp32）/ UB 中间缓冲 | 等价替换 | 累加顺序变化需评估精度影响 |
| persistent kernel | `T.Persistent` | 等价替换 | — |
| fused epilogue | `store_fixpipe` 后 UB 后处理 / CV 融合 | 等价替换或重新设计 | 取决于融合点在 Cube 侧还是 Vector 侧 |
| grid-stride loop | block 内循环处理多任务 | **重新设计** | 一维 block 任务映射 |
| 三维 Kernel（`T.Kernel(m,n,b)`） | 三维乘积展开为一维 block 数 | **重新设计** | 本项目不支持三维 Kernel（见 ascend-constraints.md） |
| online 算法 / 分块累加 | 同款算法结构 | **保留** | 纯算法层，与硬件无关 |

### 5.4 判定规则

1. 语义层 → 无条件保留。
2. 算法层 → 检查该步骤是否依赖源硬件的布局/并行假设：纯数学顺序保留；有依赖则转入优化层判定。
3. 优化层 → 查 §5.3 映射表：有等价能力 → 等价替换；无等价且影响性能/正确性 → 重新设计；无等价且不必要 → 舍弃（写明理由）。
4. **任何处置不得改变语义层**；判定存疑时按「重新设计」处理并在 DESIGN.md §0.5 标注不确定项与依据缺口。
5. 每项判定必须写明依据（本表条目编号 / `examples/` 佐证 / `docs/` 条目），不得凭感觉判定。

## 6. NPU 算法重设计

对 §5 判定为「重新设计」的条目，逐项执行本章，产出写入 DESIGN.md §0.6。

### 6.1 重设计输入

- §0.5 中全部「重新设计」条目（含其性能意图，重设计必须承接该意图）。
- NPU 硬件约束（[decision-tree.md](decision-tree.md) §3：分形限制 / 对齐 / 各级存储容量 / 一维 Kernel）。
- 本项目 API 能力（以 `examples/` 与 `docs/Tilelang.language/` 佐证，禁止凭记忆猜 API）。

### 6.2 重设计模式库

| 模式 | 适用场景 | 设计要点 |
|------|---------|---------|
| **并行结构重设计** | block×thread 两级并行、grid-stride | 一维 `T.Kernel(total_blocks)`；元素级并行交给 Vector 向量化（`T.Parallel`）；矩阵计算交给 Cube 分形；block 数与任务映射重排 |
| **归约重设计** | warp shuffle 树形归约、跨线程通信 | block 内：UB 中转 + `T.reduce_sum/max/min`；跨 block：workspace + `T.sync_block_set/wait` 核间同步，或拆两阶段 kernel；评估累加分组变化对精度的影响 |
| **矩阵计算重设计** | 手工 mma + register tiling | `T.gemm`（Cube）+ `load_nd2nz`（NZ 布局进 L0A/L0B）+ `store_fixpipe`（L0C 出数）；满足 M/N/K 分形限制与 L0C 容量 |
| **数据搬运重设计** | cp.async + SMEM 多级流水 | 分级搬运 `GM → L1 → L0A/L0B`（Cube）或 `GM → UB`（Vector）+ `T.Pipelined`；stage 数按 L1/UB 容量与 buffer 数重新计算 |
| **跨阶段融合重设计** | 多 kernel + 全局同步、中间落回 GM | CV 融合：`Scope("Cube")` + `Scope("Vector")` + `T.sync_block_set/wait`；或单 kernel 内多阶段（L0C → UB 直连） |
| **算法替代** | 数值等价的公式变形 | 如 softmax 减 max 稳定化、分块累加重排；必须给出数学等价或容差内等价论证 |
| **host 预处理内移** | im2col 等 host 侧展开 | 优先 kernel 内展开；若保留 host 侧须遵守 host 约束（只允许 stride/shape 元数据视图操作，禁止改动输入张量真实内容，见 ascend-constraints.md §4） |

### 6.3 语义保持论证（每个重设计项必须给出）

1. **数学等价证明**，或**数值容差内等价说明**（重点评估：并行度变化 → 累加分组变化 → fp16/bf16 舍入差异）。
2. **边界语义核对**：nan/inf 传播、空维度、非整除 shape 在新算法下的行为与源算子一致。
3. **验证方式**：golden 按 §0.1 语义实现 + L0 精度对比（atol/rtol 按 dtype 标准）；不达标时回到 §6.2 换模式。

### 6.4 重设计完成标准

- 每个重设计项都有三要素：源方案 → NPU 新算法 → 语义保持论证。
- 新算法满足全部 NPU 硬件约束（能被 DESIGN.md §4 内存规划 / §5 Tiling 承接）。
- DESIGN.md §1–§7 与重设计决策**一致**：§0 判定重新设计的项，§3 API 映射 / §6 循环结构不得再照抄源方案。

## 7. 反模式（禁止行为）

- ❌ 不读源码全文，只凭函数名/公式臆测语义。
- ❌ 跳过三问解读与耦合性判定，把迁移当成"逐 API 语法翻译"。
- ❌ 照搬 GPU 优化手段（三维 Kernel、warp shuffle、SMEM swizzle、thread 级并行组织）。
- ❌ 重设计改变语义（累加顺序 / dtype / 边界行为变化而未论证精度影响）。
- ❌ golden 复刻 NPU 算法而非源算子语义（丧失验证独立性，精度对比变成自证）。
- ❌ 舍弃优化项不写理由（性能回退无法追溯）。
- ❌ 判定与后续章节脱节（§0 说重设计，§3 又照抄源方案）。
