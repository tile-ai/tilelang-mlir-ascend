# Develop 的实现、检视与验证能力增强

> **状态：已接入 develop skill。** 实现方法、正确性检视和测试可信度为内部按需参考；采集复用已有链路。来源为用户选择的 cannbot-skills，实际采用版本由用户项目固定；文档接入不代表新增设备实测结论。

## 1. 摘要

当前 develop 已负责实现、精度、性能和诊断交付，但编码定位、测试可信度和特定优化机制的实施指导仍较概括。建议从 cannbot-skills 吸收适用的方法，整理为 develop 按需加载的内部参考，增强“把方案正确实现并证明”的能力。

Harness 继续负责节点范围、候选、环境和验收；外部方法辅助编码和诊断。主要代价是平台/API 资料会随工具链变化，需要保留版本与适用条件，并避免将某个后端的规则推广到其他后端。

## 2. 背景与范围

当前入口 [harness-develop](../../assets/skills/harness-develop/SKILL.md) 已有 implement-and-validate、initial-and-validate、verify-only、collect-only 和 code-only，复用 [TileLang 开发与定位](../../assets/skills/harness-develop/references/tilelang-workflow.md)、设备验证、evaluate 和上板采集。增强这些能力不新增阶段，也不将测试从 develop 分离。

analysis 决定当前问题、可证伪机制和探索方向；develop 负责可执行实现、方案落实检查及有界修复。方案实施过程中发现 API/资源不可行，develop 可以调整等价实现细节；改变核心机制、语义、目标或冻结范围时给协调者提案，不自行切换搜索节点或修改 TASK。

本轮独立编写并接入方法性资料，不复制外部代码或要求安装外部技能。

## 3. 系统关系

```text
TASK + 已接收方案 + 父候选 + 固定环境/评测计划
                         ↓
  develop 按问题读取实现 / 性能参考 / 检视 / 测试方法
                         ↓
           独占 worktree 中实现与有界修复
                         ↓
   PRECHECK → 冻结候选 → 精度 → 性能 → 诊断交付
                         ↓
       RESULT + CANDIDATE + ANALYSIS_DATA
                         ↓
            编排 agent 接收并决定下一任务
```

并发与资源调度遵循 [任务队列设计](../scheduling/design.md)。内部能力不自行创建 agent、队列项、独立调优循环或共享账本。

## 4. 能力选择

来源：[cann/cannbot-skills](https://gitcode.com/cann/cannbot-skills)。下表描述所检查资料提供的方法，目标平台是否可执行仍按项目版本核对。

| 外部技能 | 建议采用内容 | develop 中的触发点 | 必须适配的边界 |
| --- | --- | --- | --- |
| `tilelang-op-develop` | 方案到 API/任务索引/buffer/同步/写回的落实；最早失败阶段定位；修改后全量必选精度 | implement-and-validate / initial-and-validate，或实现修复 | 文件结构、后端配置、设备访问和交付格式遵循 PROJECT/TASK，不迁入“两文件”固定结构或外部设备设置 |
| `tilelang-op-design` | tile、数据流、资源预算和同步生命周期的局部实现设计 | 已选方案仍需具体化，或 initial-and-validate | 使用已有 initial_design/analysis 输入；不强制再跑独立设计节点，不覆盖冻结方案 |
| `tilelang-performance-best-practices` | 按算子族选参考，核对参考成熟度；资源容量、buffer 版本、数据流与代码生成验证 | 优化方案涉及对应机制时按需读取 | 只采用匹配架构/后端的实现依据；模板标签不是当前任务的正确性/性能证明；不硬编码容量/核数或切换后端 |
| `tilelang-review` | 索引/尾块、整数宽度、未初始化值、数据竞争、buffer 生命周期等相关正确性检视 | 改动涉及上述风险时，在预检与失败定位中使用 | 借鉴检查方法，不嵌入外部 collector、多 agent 审查、报告框架或额外修复审批 |
| `tilelang-op-test-design` | 契约→case→断言→执行路径的对应；独立参考、所有输出、尾块、别名/原地、测试实际执行证据 | 验证适配编写、测试可信度不足、精度故障、verify-only | 既有 case/容限/参考冻结后不擅改；缺口形成提案，诊断用例标为补充证据，不替代必选验证 |
| `tilelang-op-profiling` / `ops-profiling` | 核实实际 kernel/launch 与源码身份，保留可用于归因的指标及原始数据 | collect-only 或正式验证后的诊断 | 复用当前 onboard-diagnostics 与采集 helper；不引入另一套计时、warmup、重放或性能门槛 |
| `tilelang-api-best-practices` / `tilelang-programming-model-guide` | 匹配平台时作为查询参考 | API/执行域有疑问时 | 所检查版本尚无独立 Ascend950 开发实现；950 工作流直接查项目绑定源码/后端，不设为必需依赖、不回退到 910 规则 |

性能优化 skill 中的“多方案生成、排序、机制搜索”继续由 analysis 和协调者承担。develop 可使用相关实现手段核对方案是否落实，不在一个 run 内启动无界方向搜索。上板数据解析可以复用已有 analysis 工具作为定位辅助；下一步探索决策仍由正式分析/协调流程记录。

### 4.1 按操作按需加载

| operation | 主要能力 | 交付边界 |
| --- | --- | --- |
| implement-and-validate | 局部实现设计、相关正确性检视、测试/性能/诊断 | 一个已选机制的实现与有界修复，不串入其他探索方向 |
| initial-and-validate | 算子局部设计、最小实现、独立参考和完整验证 | 原 initial_design 与能力约束继续生效 |
| verify-only | 输入/入口核对、测试可信度与验证适配 | 保持输入候选；无写权限时只提交修复需求 |
| collect-only | kernel/launch 绑定、采集能力与导出完整性 | 保持候选，采集计时不用于替换正式性能 |
| code-only | 实现方法与允许的低成本检查 | 按真实执行范围报告，不能默认启动设备验证 |

### 4.2 能力落点

优先扩展现有 `tilelang-workflow.md`，承载局部实现设计、后端依据、最早失败定位和方案落实检查。按需增加 `correctness-review.md` 与 `test-credibility.md`，分别集中说明与改动有关的正确性风险和验证证据可信度。性能资料由前者按当前机制路由；采集继续引用 onboard-diagnostics，避免维护重复脚本和规则。

入口仅保留加载条件与职责，资料放 supporting references，不复制整个外部技能集合到提示词。安装后的 Harness 可以独立运行；外部仓库存在时可查项目所选版本，缺失时使用内部方法与实际 TileLang 源码，不因为可选参考未安装而阻塞。

若以后选择分发外部原文、示例或脚本，先核对对应版本许可证并保留所需声明。本方案优先独立编写方法性内容，不将外部来源标为已经过本项目设备验证。

## 5. 不变式与要求

- **INV-1**：实现使用 TASK 固定的后端/版本与能力边界，外部 skill 不改变环境、授权或测量协议。
- **INV-2**：所有语义、参考、必选 case 与容限变更通过协调者契约流程，失败修复不降低标准。
- **INV-3**：生成代码用于定位，交付修复回到可重建 TileLang 源码；每个验证结果绑定实际候选。
- **INV-4**：阶段执行者只写获准 worktree/run，不自行派发或维护共享探索队列。
- **INV-5**：实现符合方案但无收益，与实现缺陷、测量错误、原因未知分别记录；后者不借 analysis 交接绕过接收。
- **INV-6**：能力按任务需要加载，外部例子/经验/静态检查不获得设备验证资格。

每次与实现有关的建议应明确源码位置、目标机制、受影响 case 和验证办法。简单改动使用简短记录，不强制新建全部检查表或报告。性能实施参考尤其要核对目标代码实际生成的访问、流水和同步，避免“写了某个 DSL API”就认定优化已经生效。

## 6. 接口与数据

保留 TASK/RESULT @4 和 evaluation-plan、CANDIDATE、PRECHECK、ANALYSIS_DATA。能力选择及来源放 TASK 执行方式和 RESULT 实现说明，不另建 capability 运行账本。材料引用记录技能名、平台分支、相对来源文件、实际版本/摘要和适用理由；外部版本只在私有任务产物中固定。

测试可信度结果以 case/输出/路径/断言/实际执行关联，复用现有结构化验证证据。要补必选 case 时先提出契约修订；在当前授权内的小型诊断可以记录为额外证据，不伪装成冻结验收集合的一部分。

新增能力参考不更改评测代码身份。若以后引入新的 parser/adapter 或评测行为，按当前执行控制契约固定代码、保留旧在途任务绑定，不以更新 skill 为由替换运行中的评测器。

## 7. 失败与生命周期

外部参考缺失时直接查项目源码并记录限制。API 与后端不符时停止该写法，调查当前版本支持的等价实现；没有等价实现则提交具体能力缺口。精度/实现问题留在原 develop 的有界修复内，环境或预算耗尽保留未验收检查点。

参考或容限疑似有误时保留反例和定义依据，交协调者处理，不就地更改冻结输入。若发现需要新优化机制，保存当前结果并提出新的 analysis/队列项建议。并发任务不修改兄弟候选；共享安装或资源变化按队列设计的维护规则处理。

## 8. 权限、私密信息与运行限制

内部资料不携带具体设备 ID、私人路径、固定外部 commit 或普遍适用的峰值常数。外部命令、后端设置和工具参数须由本任务环境核实后使用，不直接继承外部文件中的授权或设备映射要求。

测试规模、编译变体、参考内存和 profiler 重放均受 TASK 预算约束；能力增强不自动扩展用例全集、生成大规模参数搜索或启动仿真。

## 9. 验收条件

- **AC-1**：尾块或地址索引缺陷能得到具体源码位置、反例和修复/回归办法，既有容限不变。
- **AC-2**：新增多缓冲方案能核对各 buffer 生命周期、容量与实际生成代码，未生效时判为实现问题。
- **AC-3**：测试只检查 shape、漏掉辅助输出、原地输入被 reference 污染或目标分派未命中时，能指出证据缺口，不能报告完整精度通过。
- **AC-4**：未安装 cannbot-skills 的独立 Harness 安装能按内部参考完成相同流程；平台缺失不会触发跨架构默认 API。
- **AC-5**：verify-only、collect-only、code-only 按任务范围执行，不因加载方法而修改候选或启动未要求设备工作。
- **AC-6**：独立 develop 并发时，资料不产生额外 agent、共享输出或重复测试账本，结果可按原契约接收。

## 10. 验证方法

实施后检查技能引用、独立安装和适用性路由（INV-1/4/6，AC-4/5/6）。使用隔离 fixture 做限定场景演练：索引/尾块、缓冲复用、漏输出断言、错误分派和未命中 kernel（INV-2/3/5，AC-1/2/3）。新增可执行脚本才增加相应行为测试；不以匹配文档措辞的测试代替能力验证。

真实设备验收选择已授权任务的目标版本与 case，对照修复前后精度、性能及生成代码。静态检查通过和合成演练不证明模板在所有芯片可用。

## 11. 风险与取舍

全量嵌入外部 skill 会引入冲突的编排、输出格式、环境操作和测试协议，因此选择方法级内置与按需参考。代价是部分平台具体技巧仍需查询目标版本源码；这能保持 Harness 契约稳定，也降低资料过期时误用的风险。

开发者需要有实施自主性。等价的 tile/代码结构/局部修复可在原范围内推进，核心机制或契约改变需要新的决策记录；边界由“是否仍在验证原假设”判断，而非每次调参数都回到 analysis。

## 12. 未决项

无阻塞方向的用户问题。建议首批采用实现方法、正确性检视和测试可信度，复用已有采集链；平台专用模板保持可选参考。具体引用文件随用户选定的 cannbot/TileLang 版本核对，不在产品中固定上游 commit。

## 13. 不在范围内

整体安装 cannbot-skills、复制其 agent 编排/collector、独立新增 test 节点、替换 Harness evaluate、改性能目标、自动设备重配和全量参数搜索。
