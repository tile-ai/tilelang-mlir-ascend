# Harness 工程审查与整改状态

状态：初次审查后已按 H01–H09 实施一轮修复。本文件区分已落地的工具约束、仍由宿主执行的检查和待验证能力。具体算子、机器、版本和实验原始记录保留在私有 `.workspace/` 中。

## 当前判断

当前 harness 已从主要依靠技能说明推进，补到了**有结构化接收、失败出口和可恢复控制账本的宿主驱动工作流**。十三项 skills、五个工作节点、项目隔离与生命周期、搜索知识账本及采集脚本保持原有分工；新工具复用现有项目与搜索记录，没有另建调度服务。

本轮优先解决了可在仓库内独立完成的缺陷：未知版本拒绝、评测依赖冻结、候选与逐 case 证据校验、独立晋升、安全关闭、步数与资源账本、作业状态恢复、本地进程回执、安装升级回滚，以及无性能源码时的初版路径。新增约束不要求常规开发重复审批，授权沿用用户实际指令和项目约定。

**完整实卡自主闭环仍未验收。** Linux 前台进程 runner 不负责通用 NPU ABI/launch、远端锁、SSH/容器退出层和设备回执。结构化报告能被核对，不意味着报告中的 tensor 比较、模型假设或外部作业状态已经被独立证明。后续重点应是把真实适配器接上现有契约并验收，不继续仅增加文字约束。

按 `harness-engineering` 的四类控制面评估：

| 控制面 | 当前实现 | 保留边界 |
| --- | --- | --- |
| 冻结 | TASK @4、评测 plan、显式递归依赖索引、候选 source/build/launch、评测脚本和 skill 包摘要 | 未声明依赖不能自动发现；hash 不认证执行者，也不能阻止同一写入者同时篡改内容与账本 |
| 可编辑 | 项目独立 worktree、节点白名单、批次隔离、候选快照 | 合作执行者模型；文件锁仅串行化 helper，不能阻止任意 shell 写入或提供设备隔离 |

## 1. H01/H02：评测冻结与结果验收

初次审查确认：旧 helper 主要核对声明与直接摘要，无法识别“RESULT 写 passed、证据属于另一候选或写 failed”的不一致；显式未知 TASK 版本也可以登记。该结论描述修复前实现，旧路径通过显式 legacy 保留兼容，不获得新版晋升资格。

当前实现见 [searchctl](../assets/skills/harness-resume/scripts/searchctl.py)、[evidence](../assets/skills/harness-resume/scripts/evidence.py) 和 [执行控制契约](../assets/skills/harness-resume/references/execution-control.md)：

- 新 TASK/RESULT 使用 @4；显式未知或重复版本拒绝。旧 @1–@3/无版本记录仅允许显式 legacy 补登记，不能把 @4 降级。
- 执行前固定 requirements/reference/comparator/cases/protocol/environment、必选 case/输出、统计方式、最小样本数及逐 case 最大耗时。多文件依赖通过 artifact-index@1 显式递归冻结。
- 接收核对 project/run/candidate/request、候选 source/build/launch 摘要、执行回执、全部必选输出、有效样本和诊断清单；重算 mean/median 与目标判定。accuracy/performance 声明必须与完整 validation 清单一致。
- verify-only/collect-only 固定确切输入候选。code-only/collect-only 不授予本轮正式精度/性能资格，也不能晋升最佳。
- run 固定评测器脚本和随包资产身份。运行中更换规则会阻止接收；使用原包继续，或安全关闭后新建任务。已接收历史记录不要求与当前包相同，但仍检查它原有证据。
- promote-candidate 独立于 accept。有效但未达目标的初版或优化思路可以交回 analysis，不能成为 best。已有 best 与新候选必须使用同一比较契约。

**剩余边界。** 当前精度报告是冻结比较器产生的布尔结果；helper 不重跑任意 tensor 比较，也不认证报告来源。性能仅支持固定的 mean/median 和逐 case latency 上限；相对目标须在冻结 protocol 中保存标杆、换算与依赖。权重汇总、统计显著性、跨比较契约的 best 迁移未实现。诊断清单存在不证明覆盖所有 core/pipe。完整 PRECHECK/DELIVERY 和实现归因仍由协调者复核。

**后续验收。** 接上真实适配器后，用已知正确/错误候选、缺失输出、旧二进制、新协议、无效回执分别证明拒绝边界；不能仅靠合成 JSON 证明实卡正确性。

## 2. H03：执行入口与回执

新增 [runctl](../assets/skills/harness-develop/scripts/runctl.py) 及 [使用说明](../assets/skills/harness-develop/references/local-runner.md)：执行已有 Linux 前台 argv 命令，检查 owner、项目状态与输入摘要；先持久化唯一 request，再启动独立进程组；保存 stdout/stderr、退出码、超时和进程身份。同请求重复调用只查询原结果，缺失终态回执时保留 unknown，不重新执行。

本地测试实际启动 CPU 子进程，检查非零退出传播、超时和重复调用只执行一次。输出使用 process-receipt@1，明确 local_process_only/device_validation=not_evaluated，不能用于冒充 execution-receipt@1。

**剩余边界。** 当前不处理 SSH/container/NPU 的逐层退出、共享设备锁、运行 ABI、非零 local memory、环境激活和跨机结果回收。不支持脱离进程组的后台 daemon；控制进程被强杀后不能保证清理，也不能以本地超时推断远端已退出。通用 runner 不应通过接受任意命令并手填 valid=true 来宣称设备适配完成。

**后续验收。** 按 M2 优先贯通一个实际执行组合：编译端导出 launch 元数据 → 适配器消费 → 正确性与采样 → 独立设备回执 → @4 接收；覆盖初始化失败、非零退出、控制端断线和两个串行任务的回执互不覆盖。

## 3. H04：失败任务与范围替代

新增 close-run，在执行者停止、job 终结、资源结算后，将未接收 run 关闭为 rejected/abandoned/superseded；保存不可变检查点、原因与核验依据，superseded 关联新的后继 ID。RESULT 不被改成通过，TASK 不被重写，关闭 analysis 不能充当已接收方案。

策略切换和新批次接受 accepted 或安全 closed 的完成状态；失败成员关闭后保留兄弟结果。项目冻结/归档同时检查控制账本的未结 job/预留，不能靠空检查点列表放行。未接收 run 的评测输入漂移可以报告并安全关闭，不再强迫使用旧范围通过验收。

**剩余边界。** writers_stopped 与关闭依据必须来自真实核验。已接收证据、候选或历史 TASK 被破坏属于记录完整性故障，应恢复原产物并调查，不能通过 close-run 清除已存在证据的校验失败。

## 4. H05：机制查重、淘汰与简化

新增 mechanisms 只读入口和可选 search-plan@1。计划包含 mechanism_id、预期、证伪条件、keep/discard、simplification、历史节点和新证据。相同机制必须列出已有节点，并提供新增证据或变化条件；只换一个节点 ID 重复同机制会被拒绝。analysis 已接入这一入口。

**剩余边界。** 旧历史不强制补造计划；该校验只比较稳定 ID，无法自动识别改名后的语义重复。必须有意义的消融、复杂度比较及收益相当时优先简化仍属于分析决策，不为满足字段强制消耗设备预算。未实现自动策略评分、MCTS 或无依据的定期上板。

## 5. H06：控制账本与恢复

新增 [control](../assets/skills/harness-resume/scripts/control.py)，作为现有 tree.json 的可选控制域，沿用同一锁、原子提交和 event_id 幂等机制。新 automatic 批次在安全边界启用，旧人工账本先核对真实余额后显式接入。

- run 按节点计步，批次按成员计步；失败/关闭不退还步数。恢复不清零，扩额必须带真实决定快照。
- 原子预留资源；unknown/在途 job 保留预留，结算前必须终结全部相关 job。真实超支照实登记，不能隐藏为原额度。
- 提交前登记 intent；每次状态变更绑定独立、带时区且不倒退的 job-observation，暂停阻止新增 run/预留/job，允许查询、回收和结算。
- 接收、关闭和归档检查已登记的作业/资源。reconcile 输出事件水位、未结/关闭任务、best、输入漂移、预算和旧规则接收。

**剩余边界。** 账本只约束通过工具登记的动作，不能自动拦截宿主任意 shell 或发现未登记作业；真实观察与实际用量仍需适配器。reconcile 不解析任意 STATE/AUTOMATIC Markdown、不查询远端，也没有共享环境发布锁。节点登记步数与宿主问询/恢复控制动作不是同一计数，后者继续按运行模式记录。摘要需由协调者根据水位更新。

**验证记录。** 本轮本地执行 `python3 -m unittest discover -s tests`，**91 项全部通过**（修复前 60 项，本轮新增 31 项）。测试使用临时项目、合成评测数据和真实 CPU 子进程；没有运行 NPU，也没有升级任何用户实际项目。安装后 @4 CLI 接收测试从独立目录运行，不依赖源码 checkout 的 Python 导入路径。另已检查修改文件的 Python 语法、189 个本地文档链接、AGENTS 产品区块同步及 git diff 空白错误。

## 7. H09：没有性能源码时的初版路径

新增 develop 的 initial-and-validate，接到 baseline、port、develop、next-action 与产品入口。前提是有限来源调查完成、没有适用高性能源码，且独立正确性参考、case、协议、明确目标和初版设计已固定。使用 absolute/model，明确不要求性能的任务使用 none；不能把未经测量的模型称为已测标杆。

初版仍遵守 TileLang/AICPU、融合与计时约束、低成本预检、全部必选精度、有效测量及必需诊断。实现符合初版方案且结果有效时可带目标差距进入 analysis；实现/精度/测量错误不因此免检。已有候选继续常规迭代，不用初版模式绕过优化归因。

**剩余边界。** 工具只固定方案与目标，不证明参考独立、模型准确或目标可达。不得自行虚构用户验收比例；这些内容来自已明确需求，缺少且影响结论时才补问。
