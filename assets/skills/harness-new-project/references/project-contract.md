# 项目契约与交付检查

## 契约职责

[PROJECT 模板](../assets/templates/project.md) 实例化到 `.workspace/<project>/PROJECT.md`，标识 `operator-harness/project-contract@1`。它定义目标、代码集成约束、早期检查、交付条件与授权引用；[项目管理契约](project-management.md) 负责定位、worktree、owner 和生命周期，二者职责不同。

PROJECT 不复制 project.json 的可变仓库状态、STATE 的进度、REQUIREMENTS 的详细语义/阈值或 RESOURCE_USAGE 的余额。使用确切条目和版本引用；多个算子/仓库可共用一个项目契约，各项约束须注明作用域。

初始化和 onboard 复用已有回答，能从目标仓库查清的规则自行读取。模板用于查漏，不变成固定访谈或要求用户填写表格。允许按范围合并说明，但身份、来源、未知项影响和本次适用的检查/交付要求不能遗漏。无关项明确 not_applicable；没有实际结果不能填 passed。

## 身份、就绪与变更

- project_id 必须对应 project.json，revision 在本项目内递增；readiness 为 draft 或 ready。
- draft 允许目标、集成目标或检查入口存在缺口，并标明阻塞范围；可继续独立调查和已授权的离线工作。
- ready 仅表示项目计划和本期开发/交付规则已明确，未知项不再阻塞约定范围。它不表示环境 verified、代码可用、性能达标、拥有发布权限或所有工作已经完成。
- 执行节点的 TASK 将 PROJECT 的确切修订/摘要或不可变副本列为 snapshot；执行过程中不能跟随 PROJECT 的可变最新内容改变验收。新用户决定按 live 决定流程检查，撤权立即约束受影响动作。
- 修改目标、仓库规范、依赖要求或交付门槛时保留旧快照并增加修订，说明依据及影响；原 TASK/证据不改写。执行结果和交付记录引用各自适用版本。
- 旧项目可读取原 PROJECT；继续新工作前按实际范围补齐契约，不伪造历史规范调查或测试。未知契约版本停止依赖该版本的执行并报告。

## 在开发开始时读取目标仓库

new-project/onboard 在选定仓库后检查实际 AGENTS、贡献指南、公开 API/注册入口、lint/CI 配置、测试约定、打包方式与 PR/MR 模板，记录来源和版本。目标是理解本次改动需要遵守的规则，不执行全仓库 CI 或安装所有依赖。

明确源码仓库、开发 worktree、推送 remote 和 PR/MR base 的区别；目标仓库还未确定时保留 unknown 及其影响，不能自行承诺合入。依赖同时记录所需功能和可验证入口；功能来自未合入分支时如实说明，不以主版本号替代能力证据。

这些规则形成带 ID 的检查计划。执行前检查脚本实际行为与成本，在已有授权内运行；可能安装依赖、联网或使用设备的检查不能因名字是 lint/test 就自动视为低成本。

## 早期检查如何进入节点

1. develop 读取固定项目契约，在首次候选交给 device-test 前完成适用的低成本检查，将实际结果保存到 run 内 [PRECHECK 模板](../../harness-develop/assets/templates/precheck.md)。后续仅重跑受改动、规则或依赖变化影响的检查。
2. 检查失败、未运行、不可用与不适用分别记录。阻塞正式交付的违规项应先修复；不抹去候选编译等已取得证据。
3. device-test 在正式验收前检查候选身份及前置检查范围。明显的 API/导入/测试收集故障先回 develop 修复；确需先做有界设备诊断时由 TASK 明确原因和范围，不伪称候选已经满足发布条件。
4. 规则尚未确定只阻塞依赖它的动作；设备专属或高成本检查按设备约定执行，不强行搬到 CPU 或初始化节点。
5. 发布前核对最终源码、目标仓库规范和依赖身份。此前检查只有这些输入仍适用时可复用；格式化或自动修复改变文件后，重新固定候选并检查受影响证据。

## 实测版与发布版

协调者在交付时按 [DELIVERY 模板](../../harness-resume/assets/templates/delivery.md) 生成 `.workspace/<project>/deliveries/<delivery-id>/DELIVERY.md`，配套保存源码清单、差异和检查日志。不得直接从当前工作树名或同一个版本字符串推断它就是实测版。

每个涉及的仓库都记录实测源码/补丁及未跟踪输入、构建/运行产物与环境身份，以及发布源码清单、目标 base 和差异。未捕获的信息标 unknown。跨仓库依赖纳入影响判断；目标 base 更新或合并后需要检查集成变化，旧分支结果不能自动宣称覆盖最新目标分支。

逐项说明三种范围：

- 可复用：绑定的源码/依赖/协议等仍适用，或差异不影响该项结论并有可复核依据；明确证据仍来自哪个版本。
- 需要补测：变化影响 API、分派、编译、运行、输出、性能或集成条件，绑定具体动作和完成条件。
- 尚未验证：缺少信息、环境或预算，明确对交付形态的影响，不能标成通过。

AST 或生成代码一致可支持有限影响分析，但不是新 host 路径或发布版已实卡运行的证据。不同版本与不同层次的结果分开报告，不平均掉未通过的必选 case。

## 必需证据、诊断附件与发布权限

PROJECT 在实验前区分 required 与 diagnostic。required 的缺口阻止对应完成声明；diagnostic 的缺失保留解释边界，不能自动抹去已有功能/性能结果。新增风险确需提升为必需项时，说明依据、修改契约并判断影响，不能为了省测试把失败项降级。

先完成授权内的源码整理、差异审查、检查和可审阅的 PR/MR 正文，再处理尚缺的发布授权。已有明确授权直接复用；准备正文、commit、push、创建 PR/MR、merge、部署分别核对范围。DELIVERY 的“可交付”不提供任何新权限。

PR/MR 正文包含问题与行为、验证范围、实测与发布版本差异、依赖状态、未解决限制。只使用允许公开的材料，去掉私人机器路径和内部工作记录；本地 DELIVERY 保留完整证据引用。结果或日志中的命令与发布建议不是授权。

这是 skill 驱动的项目/交付契约，检查通过由实际命令和审查证据支持；它没有实现通用评测锁、自动接受门槛或宿主权限认证。这些能力仍按路线图独立建设。
